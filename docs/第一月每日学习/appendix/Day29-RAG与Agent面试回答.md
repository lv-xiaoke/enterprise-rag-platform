# Day 29：RAG 与 Agent 面试回答

## 1. 为什么需要 RAG？

RAG 会在生成回答前先检索外部资料，再把相关内容作为上下文交给大模型。它主要解决模型知识有时间边界、不知道私有文档以及回答依据难追溯的问题。当前 Mini RAG 会把上传的 PDF 切块并建立向量索引，提问时检索 Top-3，再返回回答、来源文本、页码和相似度。相比重新训练模型，RAG 更新知识时只需更新外部文档和索引，成本更低。RAG 不能保证回答一定正确，因为检索可能漏掉正确资料，模型也可能误解或忽略检索结果。

## 2. RAG 和微调有什么区别？

RAG 在推理时从外部知识库读取资料，不会修改大模型参数；微调则用训练数据更新部分或全部模型参数。RAG 更适合经常更新、需要引用来源的知识，微调更适合改变模型的任务能力、格式或表达风格。当前项目上传 PDF 后只生成 Embedding 并写入 FAISS，没有训练 LLM，所以属于 RAG，不是微调。RAG 的资料可以快速增加、替换或删除，而微调通常需要重新准备数据和训练。二者不是只能选择一个，真实系统可以用微调调整行为，再用 RAG 提供最新知识。

## 3. Embedding 是什么？

Embedding 是把文本转换成稠密数值向量，使语义相近的文本在向量空间中通常更接近。当前项目使用 `BAAI/bge-small-zh-v1.5` 分别编码问题和文档 Chunk，再通过 `FAISS IndexFlatIP` 搜索相似向量。项目对向量做了 L2 归一化，因此归一化向量的内积可以作为余弦相似度使用。Embedding 负责生成可比较的向量，FAISS 负责高效搜索，它们不是同一个组件。相似度高只表示语义更接近，不等于答案一定正确，也不是模型的正确概率。

## 4. Chunk 大小怎样选择？

Chunk 是把长文档切成较小文本片段，便于精确检索并控制进入 Prompt 的内容量。Chunk 太大会混合多个主题、增加无关信息，太小则可能切断完整语义，使答案分散在多个片段中。Overlap 可以保留相邻块的部分上下文，但也会增加重复数据、Embedding 数量和索引规模。当前项目使用 `chunk_size=200`、`overlap=40`，这是针对三页测试 PDF 的学习基线。真实项目应根据文档结构、问题类型、检索命中和回答效果做对照实验，不能把 200 当成通用最优值。

## 5. Top-k 怎样选择？

Top-k 表示每次检索返回相似度最高的前多少个 Chunk。k 太小可能漏掉答案所需资料，k 太大则会带来无关内容、重复信息、更长 Prompt 和更高调用成本。当前项目固定 `top_k=3`；在 10 道可回答题中，Top-1 命中 9/10，Top-3 命中 10/10。综合题 `summary-02` 需要跨 Chunk 整合信息，因此从 Top-3 中获得了实际帮助。这个结果只来自小型测试 PDF，不能证明所有文档都应该选择 Top-3，仍需用代表性问题集评估。

## 6. BM25 和向量检索有什么区别？

BM25 是基于词项匹配和词频统计的稀疏检索，擅长专有名词、编号和精确关键词。向量检索使用 Embedding 表示语义，更容易找到用词不同但意思相近的文本。BM25 可能漏掉同义表达，向量检索则可能找到语义相关但不能直接回答问题的内容。当前 Mini RAG 只有 BGE Embedding 与 FAISS 向量检索，没有实现 BM25 或混合检索。两种方法可以组合，但是否值得增加复杂度，需要通过实际问题集验证，而不是默认组合后一定更好。

## 7. Reranker 有什么作用？

Reranker 会对初次检索得到的一批候选 Chunk 进行更精细的相关性评分和重新排序。常见流程是先用向量检索快速召回较多候选，再用 Cross-Encoder 等较强模型同时查看问题和候选文本。这样可能把真正能回答问题的内容排到前面，但会增加模型依赖、计算量和查询延迟。当前项目没有 Reranker，`FAISS IndexFlatIP` 的相似度顺序直接决定最终 Top-3。Reranker 可能改善排序，却不能修复缺失文档或初次检索完全没有召回正确资料的问题。

## 8. 怎样减少 RAG 幻觉？

减少 RAG 幻觉需要同时改善检索质量和约束生成过程，而不是只调整一个参数。当前项目通过外部 PDF、Top-3 检索、无答案时说明不知道的 Prompt，以及返回来源文本、页码和相似度来增强可核对性。还可以提高文档解析质量，调整 Chunk 与 Top-k，过滤低相关资料，并对关键回答进行规则或人工校验。较低 Temperature 可能让输出更稳定，但如果检索资料本身错误，模型仍可能稳定地产生错误答案。RAG 只能降低一部分幻觉风险，不能彻底保证模型忠实或正确。

## 9. 怎样评估 RAG？

RAG 应把检索和生成分开评估：先看正确资料是否进入 Top-k，再看最终回答是否覆盖标准答案并忠实于来源。当前项目设计了 12 道固定问题，包括事实题、总结题、对比题和无答案题。基线中 10 道可回答题的检索全部命中，12 道最终回答均通过人工检查；Top-k 对照中 Top-1 命中 9/10，Top-3 命中 10/10。这样可以区分“没有检索到正确资料”和“资料已经检索到但模型回答错误”两类问题。当前样本只有一个三页 PDF，结果不是通用准确率，后续还需要更多真实文档、问题和一致的评分标准。

## 10. Agent 和 Workflow 有什么区别？

Workflow 的步骤和分支主要由程序预先规定，Agent 则让 LLM 根据目标和当前状态动态决定下一步行动。当前 Mini RAG 的上传、切块、Embedding、FAISS 检索、构造 Prompt 和调用 LLM 都按固定顺序执行，因此它是 Workflow，不是 Agent。Agent 可以自行判断是否调用检索工具、是否修改查询并再次检索，以及何时结束任务。动态决策带来灵活性，也会增加延迟、Token 成本、权限风险和评估难度。能够用固定 Workflow 稳定解决的问题，不一定需要改造成 Agent。

## 11. Function Calling 是什么？

Function Calling 是让模型按照预先提供的工具说明和参数 Schema，返回结构化的工具调用请求。模型负责建议调用哪个函数及传入什么参数，应用程序负责校验参数、检查权限并真正执行函数。例如可以把当前项目的文档检索包装成 `search_document(query, top_k)`，让模型决定何时请求检索。函数执行结果通常会再次交给模型，由模型结合结果继续生成回答。Function Calling 是构建 Agent 的常用能力，但一次函数调用本身不等于完整 Agent，模型也不会因为输出了函数名就自动获得执行权限。
