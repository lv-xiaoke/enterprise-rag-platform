## 一、这份文件负责什么

这份文件是当前项目的“每日任务总表”，用于规定 Day 1～Day 17 每一天的目标、边界、产物、验收证据和前后依赖。

三类文档的职责如下：

- `docs/17天-基础知识地图.md`：解释项目架构、核心概念和两条主链路。
- `docs/17天-当前项目每日安排.md`：规定每天做什么，以及做到什么程度才算完成。
- `docs/17天每日学习/DayXX.md`：根据本安排和仓库实时状态生成的当天详细操作计划。

本文件不展开大段代码，也不代替当天教程。后续生成 `DayXX.md` 时，应把本文件作为任务约束，把基础知识地图作为概念背景，再通过只读检查仓库确定真实起点。

## 二、事实与状态判定规则

### 2.1 事实优先级

如果文档描述与仓库现状发生冲突，按下面的顺序判断：

```text
真实运行结果和可复现证据
> 当前代码、迁移、配置和测试
> 本文件规定的目标与完成标准
> 已生成的 DayXX.md 和手工学习记录
```

`DayXX.md` 已经存在，不代表当天任务已经完成；代码已经写入，也不代表功能已经通过验收。

### 2.2 状态只使用以下五种值

| 状态  | 含义                          |
| --- | --------------------------- |
| 未开始 | 当天核心产物尚未形成，即使存在可复用旧代码也不能算开始 |
| 进行中 | 已有与当天目标直接相关的实现，但尚未满足完整完成标准  |
| 待验收 | 核心实现基本存在，只缺真实运行、边界测试或证据记录   |
| 已完成 | 代码、正常路径、失败路径和证据均满足当天完成标准    |
| 阻塞  | 已确认存在无法在当前条件下继续解决的外部阻塞      |
|     |                             |

### 2.3 更新状态时必须保留证据

将某一天改成“已完成”时，至少记录：

- 实际修改或新增的关键文件。
- 正常路径的真实命令与结果摘要。
- 一个与当天主题相关的失败或边界路径结果。
- 数据库、HTTP 响应、pytest、评测报告或重启结果中的至少一种可核对证据。
- 如已提交，记录真实 Git commit；未提交不能虚构。

## 三、当前项目真实起点

以下结论来自 2026-08-31 对当前仓库的只读检查，不代表未来状态；后续生成每日计划时仍需重新检查。

### 3.1 已经具备的 FAISS 基线

- FastAPI 已提供 `/upload` 和 `/rag/chat`，能够完成 PDF 解析、Chunk 切分、Embedding、FAISS 检索和 LLM 回答。
- `BAAI/bge-small-zh-v1.5` 生成 512 维向量，当前检索默认使用 Top-3。
- 回答来源已经包含 Chunk 原文、PDF 页码和相似度。
- 已有一个单 PDF 的固定问题集、基线结果和 Top-1/Top-3 对照脚本。
- 当前只保留最近一次成功上传的内存 FAISS 索引，服务重启后需要重新上传。
- SQLite 目前只保存普通聊天历史，不负责企业知识库、文档、Chunk 或向量持久化。

### 3.2 已经开始的 PostgreSQL 升级

- `requirements.txt` 已声明 SQLAlchemy、psycopg、pgvector 和 Alembic。
- `docker-compose.yml` 已提供带持久化 Volume 的 `pgvector/pgvector:pg16` 数据库服务。
- `app/db.py` 已出现 PostgreSQL URL、Engine、Session 工厂、ORM Base 和连接探针。
- Alembic 已初始化，并存在启用 PostgreSQL `vector` 扩展的基线迁移。

### 3.3 尚未形成的新架构能力

- 尚未看到 `KnowledgeBase`、`Document`、`Chunk` 三个 SQLAlchemy ORM 业务模型及对应建表迁移。
- 尚未形成面向知识库、文档和 Chunk 的 Repository 层。
- PDF 入库仍写入内存 FAISS，没有把文档元数据、页码、Chunk 和向量写入 PostgreSQL。
- RAG 检索仍使用 FAISS，没有按知识库和文档状态执行 pgvector Top-K 查询。
- API 仍是单文档 `/upload`、`/rag/chat`，没有多知识库和多文档管理接口。
- 尚未看到覆盖新架构关键场景的 pytest 测试。
- 现有评测是单个小型 PDF 的旧基线，不是新的企业制度多文档评测集。
- README 仍主要描述 FAISS 版本，不能作为 pgvector 版本已完成的证明。

因此，本文件初始化时将 Day 1 标为“进行中”，Day 2～Day 17 标为“未开始”。后续只能根据新增的真实证据更新状态。

## 四、17 天最终目标和范围

### 4.1 最终交付目标

17 天结束时，项目应成为一个可演示、可评测、可复现的企业知识库 RAG 后端：

```text
创建知识库
→ 上传多份 PDF
→ 解析并切分 Chunk
→ 生成 512 维 Embedding
→ 文档、Chunk、页码和向量持久化到 PostgreSQL + pgvector
→ 在指定知识库内检索 ready 文档
→ 基于 Top-K Context 调用 LLM
→ 返回回答、文档名、页码、Chunk、原文和分数
→ 证据不足时拒答
```

最终还必须留下：

- 一套企业制度演示 PDF。
- 一套固定评测集和可重复运行的评测报告。
- 覆盖关键链路的 pytest 测试。
- 多文档与服务重启后的持久化验收证据。
- 面向求职的 README、架构图、三分钟演示和独立简历条目。

### 4.2 最小实现范围

必须完成：

- `KnowledgeBase → Document → Chunk` 三层数据关系。
- PostgreSQL + pgvector 持久化。
- 多知识库隔离、多文档上传和文档状态过滤。
- 文档入库、向量检索、RAG 回答、来源追溯和无答案拒答。
- 事务、失败状态、输入校验、固定评测、pytest 和重启恢复。

### 4.3 本轮明确不做

- OCR、扫描件、复杂表格和多模态解析。
- 登录、权限、租户计费和管理后台前端。
- Celery、消息队列、分布式任务和复杂微服务拆分。
- PostgreSQL 高级性能调优、复杂事务隔离级别和大规模压测。
- 为了展示技术数量而增加与核心链路无关的框架。

如果进度延误，优先取消高级向量索引优化、健康检查细化和 Docker 启动体验优化；不得挤占 Day 15～Day 17 的文档、演示和面试准备时间。

## Day 1：建立 PostgreSQL 连接与可回滚迁移基线

- 所属阶段：数据基础
- 当前状态：进行中
- 所属链路：支撑两条核心链路的数据库基础设施
- 建议用时：60 分钟

### 1. 当日目标

让 Python 应用能够安全连接 PostgreSQL，并使用 Alembic 管理可升级、可回滚的 `vector` 扩展基线。

### 2. 为什么现在做

后续模型、Repository、文档入库和向量检索都依赖稳定的数据库连接与迁移机制；Day 1 的输出是 Day 2 建表的前提。

### 3. 开始前应具备的输入

- 可运行的 Python 环境和当前项目依赖文件。
- 可用的 Docker Desktop 或等价 PostgreSQL + pgvector 环境。
- 通过环境变量提供的数据库配置；不能读取、记录或输出真实密码。

当前已有 `app/db.py`、数据库 Compose、Alembic 配置和 vector 扩展迁移，但尚无完整验收证据，配置缺失校验也需要复核。

### 4. 当日唯一核心产物

一套可以完成连接探针以及 `upgrade → downgrade → upgrade` 的 PostgreSQL/Alembic 基线。

### 5. 学习重点

- PostgreSQL、psycopg、SQLAlchemy 三者的职责边界。
- Engine、Connection、Session 和连接池的区别。
- Alembic migration 与 `Base.metadata.create_all()` 的区别。
- PostgreSQL 的 vector 扩展与 Python `pgvector` 包的区别。

### 6. 实施范围

- 检查数据库配置是否完整，错误只报告缺失变量名。
- 固定一个应用级 Engine、Session 工厂和可主动执行的连接探针。
- 确认 Alembic 从应用配置获取数据库地址，且日志不会泄露密码。
- 完成 vector 扩展基线迁移的升级和回滚定义。

### 7. 验收场景

- 正常路径：连接探针返回 `1`；迁移可以升级、回滚并再次升级到 head。
- 失败路径：数据库停止或配置缺失时快速失败，错误信息不包含真实密码。
- 证据：记录 Alembic 当前版本、vector 扩展查询结果和连接探针输出。

### 8. 完成标准

- [ ] 能解释 SQLAlchemy 为什么仍然需要 psycopg。
- [ ] 能说明 Engine 与一次请求中的 Session 的生命周期差异。

- [ ] Alembic 成功执行升级、回滚和恢复到 head。
- [ ] 数据库不可用或配置缺失时不会泄露连接密码。
- [ ] 保存了真实运行命令和结果摘要。

## Day 2：建立 KnowledgeBase、Document 和 Chunk 三张核心表

- 所属阶段：数据基础
- 当前状态：未开始
- 所属链路：文档入库与问答链路共享的数据骨架
- 建议用时：60 分钟

### 1. 当日目标

使用 SQLAlchemy ORM 和 Alembic 建立知识库、文档、Chunk 三层数据关系，并为 512 维向量持久化准备字段。

### 2. 为什么现在做

Day 1 只建立了数据库入口；Day 3 的 Repository 必须先知道数据的字段、约束和关系。

### 3. 开始前应具备的输入

- Day 1 的 ORM Base、数据库连接和可回滚迁移基线。
- 已确认 Embedding 模型输出 512 维向量。
- 对主键、外键、一对多关系和文档状态的基本理解。

### 4. 当日唯一核心产物

包含三张业务表、外键、状态约束、常用查询索引和 `vector(512)` 字段的可回滚迁移。

### 5. 学习重点

- SQLAlchemy ORM 模型与 Pydantic 请求/响应模型的区别。
- 主键、外键、唯一约束、检查约束和索引分别解决什么问题。
- `KnowledgeBase 1:N Document 1:N Chunk` 的级联和生命周期边界。
- 为什么向量字段维度必须与模型输出一致。

### 6. 实施范围

- KnowledgeBase：唯一身份、名称、描述和创建时间等最小字段。
- Document：所属知识库、文件名、处理状态、失败原因和时间字段等最小元数据。
- Chunk：所属文档、页码、顺序、原文和 512 维 Embedding。
- 注册 ORM 元数据并生成、检查、升级、回滚和恢复迁移。

### 7. 验收场景

- 正常路径：迁移后数据库真实存在三张表、外键、约束、索引和 512 维向量字段。
- 失败路径：非法文档状态或无效外键不能写入。
- 证据：数据库结构查询和迁移往返结果。

### 8. 完成标准

- [ ] 能画出三张表的一对多关系。
- [ ] 能解释 ORM 模型与 API Pydantic 模型为什么不能混为一谈。
- [ ] 三张表通过 Alembic 迁移真实创建。
- [ ] 外键、状态约束、页码约束和向量维度符合设计。
- [ ] 非法状态或无效外键写入失败。
- [ ] 迁移能够回滚并恢复到 head。

- 不编写完整 CRUD 和业务流程；Repository 属于 Day 3。
- 不提前创建 HNSW 或 IVFFlat 高级索引，除非小数据验收明确需要。

### 10. 面试输出

能够解释三张表为什么这样拆分、外键和索引为什么解决不同问题，以及状态约束为什么不能只依赖 Python。

## Day 3：建立知识库、文档和 Chunk 的 Repository 层

- 所属阶段：数据基础
- 当前状态：未开始
- 所属链路：API/Service 与数据库之间的数据访问边界
- 建议用时：60 分钟

### 1. 当日目标

把创建、查询和更新数据库记录的逻辑集中到 Repository，避免 API 和 Service 到处直接操作 SQLAlchemy。

### 2. 为什么现在做

Day 2 已固定数据形状；Day 4 的文档入库需要稳定地创建 Document、批量保存 Chunk 并更新状态。

### 3. 开始前应具备的输入

- Day 2 的 ORM 模型和已升级数据库。
- Day 1 的 Session 工厂。
- 明确 Repository 负责数据访问、Service 负责编排业务。

### 4. 当日唯一核心产物

覆盖知识库创建/查询、文档记录创建/更新、Chunk 批量保存和基础查询的最小 Repository 接口。

### 5. 学习重点

- Repository 与 Service 的职责区别。
- Session 由谁创建、传入、提交、回滚和关闭。
- `flush`、`commit`、`refresh` 的作用与时机。

## 九、每日计划自动生成规则

后续提示词根据本文件生成 `docs/17天每日学习/DayXX.md` 时，必须执行以下规则。

### 9.1 用户明确指定 Day

- 以对应 Day 的“当日唯一核心产物”和“完成标准”为边界。
- 先只读检查仓库，不让用户重复已经有真实证据的工作。
- 如果前置条件缺失，只补齐会阻塞当天目标的最小前置条件。
- 不提前实现“今日不做”中属于以后 Day 的功能。

### 9.2 用户没有指定 Day

1. 读取本文件的总览和详细安排。
2. 只读检查代码、迁移、测试、评测数据和 Git 状态。
3. 找出最早一个尚未满足完整完成标准的 Day。
4. 根据真实状态将当天计划分成“复核已有部分”和“完成缺失部分”。
5. 每次只生成一天，不直接执行当天代码升级。

### 9.3 每天必须提取的字段

```text
Day 编号和任务名称
所属阶段与所属链路
当前真实起点
当日目标
前置输入
唯一核心产物
学习重点
实施范围
正常路径
失败或边界路径
完成标准
今日不做
面试输出
给下一天留下什么
```

### 9.4 生成后的状态处理

- 新生成计划中的复选框全部保持未勾选。
- 没有实际运行的内容只能写“预期结果”或“待实测”。
- 用户完成操作并提供证据后，才能更新本文件中的“当前状态”和“实际进度记录”。
- “待验收”不能自动跳过；下一次应优先生成验收与补证据步骤。
- 工作区有用户修改时，只读识别并保护，不覆盖、不恢复、不混入无关变更。

## 十、每日收尾记录模板

完成任何一天后，在对应 Day 的“实际进度记录”中填写：

```markdown
- 实际完成：用一到三句话记录真实产物。
- 运行证据：记录命令、关键输出、HTTP 状态码、数据库结果、pytest 或评测报告路径。
- 遇到的卡点：记录真实问题；确实没有则写“暂无”。
- Git commit：填写真实 commit hash 或“未提交”。
```

更新完成后，再根据完成标准把状态改成“进行中”“待验收”或“已完成”。不得仅为了推进 Day 编号而把未验证任务标记为已完成。
