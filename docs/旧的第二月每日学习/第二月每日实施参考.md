# 第二月每日实施参考：企业制度与 SOP 智能知识库

## 一、本月目标

在现有 FastAPI、SQLite、FAISS 单文档 RAG Demo 的基础上，用 28 天完成一个可用于面试演示的企业制度与 SOP 智能知识库 MVP。

建议每天投入 2～3 小时。每天优先完成一个可以运行、检查或展示的核心目标，不要同时铺开过多功能。

月底需要形成以下成果：

- 支持多知识库、多文档和服务重启后的数据持久化。
- 支持异步文档处理、状态查询、失败重试和重新索引。
- 支持组织、部门以及 `admin`、`editor`、`viewer` 基础权限。
- 回答可以引用文档名称、版本、页码、Chunk 和原文片段。
- 资料不足时明确拒答，不使用模型常识补全企业制度。
- 具备固定评测集、自动化测试、轻量页面和 Docker Compose 启动方式。
- 具备 README、架构图、评测报告、演示脚本和演示视频素材。

## 二、第一周：多知识库与持久化

### Day 1：确认起点和月底完成标准

- 盘点当前 SQLite、全局 `rag_service`、内存 FAISS、上传接口和 RAG 问答流程。
- 记录现有接口、评测结果和主要限制，作为本月改造基线。
- 画出 PostgreSQL、pgvector、Redis、Worker、MinIO 和 FastAPI 的目标架构草图。

### Day 2：建立 PostgreSQL + pgvector 环境

- 使用 Docker Compose 启动 PostgreSQL + pgvector。
- 验证数据库健康状态、`vector` 扩展和命名卷持久化。
- 补充数据库连接所需的环境变量示例，确保不提交真实密码。

### Day 3：接入 ORM 和数据库迁移

- 接入 SQLAlchemy 2、PostgreSQL 驱动和 Alembic。
- 建立统一的数据库会话与应用启动/关闭流程。
- 完成第一个可以升级和回滚的迁移，确认应用能连接 PostgreSQL。

### Day 4：设计核心业务模型

- 建立组织、部门、用户、知识库、文档和文档版本模型。
- 明确主键、外键、创建时间、状态和版本关系。
- 确认一个知识库可以包含多份文档，同一文档可以保留多个版本。

### Day 5：设计 Chunk 和处理状态模型

- 建立 Chunk、向量、页码、标题、章节和版本来源字段。
- 增加 `pending`、`processing`、`completed`、`failed` 处理状态。
- 为知识库过滤、有效版本过滤和向量检索建立必要索引与迁移。

### Day 6：用 pgvector 替换核心 FAISS 检索

- 实现 Chunk 和向量的批量写入。
- 实现按知识库、文档状态和有效版本过滤的向量相似度检索。
- 保留现有 Embedding 和 LLM 服务，先跑通最小 pgvector 检索链路。

### Day 7：跑通多文档持久化

- 连续上传多份 PDF，并在同一知识库中完成跨文档问答。
- 重启 API 和数据库服务，确认无需重新上传即可继续检索。
- 记录第一周未完成项和技术问题，但不提前扩展异步任务或前端功能。

## 三、第二周：异步处理与基础权限

### Day 8：接入 Redis 和 Celery Worker

- 在 Docker Compose 中增加 Redis 和 Worker。
- 创建最小 Celery 任务，验证 API 可以投递任务且 Worker 可以执行。
- 明确任务 ID、超时、重试和日志的基本约定。

### Day 9：接入 MinIO 原文件存储

- 在 Docker Compose 中增加 MinIO，并建立原文件存储抽象。
- 上传 PDF 后保存稳定的对象键、文件名、大小和内容类型。
- 验证 API 或 Worker 可以重新读取同一份原文件。

### Day 10：文档处理任务化

- 将 PDF 解析、切块、Embedding 和 pgvector 入库迁移到后台任务。
- 让上传接口立即返回文档 ID 和任务 ID，不再等待完整处理结束。
- 确认处理成功后才把文档版本标记为可检索。

### Day 11：完善状态、重试和重新索引

- 保存任务开始时间、完成时间、失败阶段和失败原因。
- 实现失败任务的安全重试和文档重新索引入口。
- 保证重复执行任务不会生成重复 Chunk，也不会破坏上一个可用版本。

### Day 12：实现用户登录和 JWT

- 建立用户密码哈希、登录和 JWT 签发/校验流程。
- 为受保护接口增加当前用户依赖。
- 创建最小演示账号，验证错误密码、过期 Token 和未登录访问会被拒绝。

### Day 13：建立角色和访问关系

- 建立 `admin`、`editor`、`viewer` 三类角色。
- 明确组织、部门、知识库和文档之间的可见关系。
- 让管理员管理知识库和用户，编辑者管理文档，查看者只进行查询和问答。

### Day 14：把权限落实到检索条件

- 在文档列表、状态操作和 RAG 检索前执行组织、部门和知识库权限过滤。
- 验证系统不会先检索全部数据、再在响应阶段隐藏无权来源。
- 完成同组织跨部门、跨组织和不同角色的越权测试。

## 四、第三周：引用、拒答与 RAG 评测

### Day 15：准备制度与 SOP 演示数据

- 制作 10～12 份标记为虚构演示数据的企业制度或 SOP 文档。
- 至少准备两组新旧版本，以及财务、HR、行政等不同部门可见资料。
- 统一文档名称、版本、生效日期、状态和预期访问范围。

### Day 16：升级结构化切块

- 从固定字符切块升级为保留标题、章节、Token、页码和版本的结构化切块。
- 保留适当重叠，避免制度条款或操作步骤在 Chunk 边界被截断。
- 抽查多个 Chunk，确认正文与来源元数据可以一一对应。

### Day 17：完善回答引用

- 扩展 RAG 来源，返回文档 ID、名称、版本、页码、Chunk ID、原文片段和分数。
- 在 Prompt 中给上下文编号，让回答结论能够对应具体来源。
- 验证同一答案引用多个文档时，来源顺序和内容不会混淆。

### Day 18：建立 30 道固定评测题

- 建立 30 道问题及标准答案、预期文档和证据标注。
- 覆盖单文档事实、流程、跨文档、版本、权限和无答案问题。
- 固定数据集版本、Chunk 参数和 Top-K，运行并保存 pgvector 向量检索基线。

### Day 19：增加无答案判断和拒答

- 根据评测结果确定相似度阈值和无答案判断流程。
- 资料不足、权限不足或只有无关 Chunk 时，明确说明知识库没有足够依据。
- 检查拒答不会泄露无权限文档的名称、片段或存在性。

### Day 20：实现混合检索

- 使用 PostgreSQL 全文检索补充关键词、制度编号和专业术语召回。
- 将全文检索与向量检索结果按固定规则融合并去重。
- 使用同一套 30 道题与基线对比，不根据单个演示问题临时调整参数。

### Day 21：评估 Reranker 并形成报告

- 对比纯向量、混合检索和加入 Reranker 后的 Recall@5、引用正确率与延迟。
- 只有在 Recall@5 明显提升且延迟可以接受时，才把 Reranker 保留在默认链路中。
- 保存参数、运行时间、真实结果和失败案例，形成第一版评测报告。

## 五、第四周：页面、工程化与作品集

### Day 22：建立轻量页面框架

- 使用 FastAPI、Jinja2 和少量前端脚本建立登录页、导航和基础布局。
- 按管理员与员工划分页面入口。
- 完成加载、空状态和通用错误提示样式。

### Day 23：完成管理员文档页

- 支持选择知识库、上传 PDF、查看文档列表和处理状态。
- 支持查看版本、失败原因、停用文档和重新索引。
- 验证不同角色只能看到和执行自己有权限的操作。

### Day 24：完成员工问答页

- 支持选择知识库、输入问题并展示回答。
- 使用引用卡片展示文档名称、版本、页码、分数和原文片段。
- 完善等待、失败、无答案和无权限状态，避免页面只在成功路径可用。

### Day 25：增加日志和健康检查

- 为每次请求生成请求 ID，并记录用户、知识库、任务和问答链路。
- 记录检索耗时、模型耗时、总耗时、Token 和可获得的费用信息。
- 将 liveness 与 readiness 分开，检查数据库、Redis、MinIO 和必要配置。

### Day 26：补齐测试和 CI

- 为数据模型、权限过滤、任务幂等、检索、引用和拒答补充 pytest 测试。
- 建立上传到问答的端到端集成测试。
- 配置 GitHub Actions，确保关键测试可以在干净环境中重复执行。

### Day 27：完善部署和作品集材料

- 完整验证 API、Worker、PostgreSQL、Redis 和 MinIO 的 Docker Compose 启动流程。
- 完善 `.env.example`、README、架构图、数据说明、评测报告和三分钟演示脚本。
- 核心验收全部通过且仍有时间时，再尝试最小飞书机器人接入；否则继续修复测试和文档。

### Day 28：最终验收与演示

- 连续完成两次“上传新版制度 → 查看处理状态 → 提问并检查引用 → 停用旧版 → 再次提问 → 无答案拒答”的演示流程。
- 只修复影响安装、登录、入库、权限、问答、引用和演示的阻塞问题。
- 录制演示视频，整理简历项目描述、真实指标、已知限制和第三个月待办。

## 六、目标接口与数据能力

- 知识库和文档：创建与查询知识库，上传、列表、停用、状态查询和重新索引。
- 登录和权限：JWT 登录，组织、部门及 `admin`、`editor`、`viewer` 角色控制。
- RAG 问答：请求明确指定知识库，在检索前执行权限和有效版本过滤。
- 来源引用：包含文档 ID、名称、版本、页码、Chunk ID、原文片段和分数。
- 异步任务：上传返回文档 ID 和任务 ID，可以查询状态、失败原因并安全重试。

## 七、月末验收标准

- 连续上传至少 10 份文档后可以跨文档检索，重启服务后数据和向量仍然可用。
- 停用旧版本后，新回答不再引用旧版；每条来源能定位到版本、页码和原文。
- A 组织或无权限部门的用户不能检索 B 组织或受限部门的资料。
- 失败任务不会破坏已完成文档，并能通过重新索引恢复。
- 30 道固定评测题可以重复运行，并报告真实的 Recall@5、引用正确率、拒答正确率和延迟。
- Docker Compose 可以启动 API、Worker、PostgreSQL、Redis 和 MinIO。
- 固定演示流程可以连续运行两次，README 中的步骤和指标都能复现。

## 八、进度落后时的取舍顺序

如果实际进度落后，按以下顺序缩减工作量：

1. 取消 Reranker，只保留已经验证有效的向量或混合检索。
2. 取消飞书机器人接入，保留 Web 演示页面。
3. 减少高级统计和费用看板，只保留结构化日志与核心耗时。
4. 管理页面缩减为上传、列表、状态、停用和重新索引。

不能取消的核心能力：多文档持久化、异步处理、权限过滤、有效版本过滤、可追溯引用、无答案拒答、固定评测、自动测试和可复现演示。

## 九、本月范围边界

- 必须支持带文本层的 PDF；Word、Excel、OCR 和复杂表格解析不作为本月硬性目标。
- 页面使用 Jinja2 轻量实现，不建立独立 React 或 Vue 工程。
- 演示资料全部使用虚构或经过脱敏且允许使用的内容，不提交真实企业敏感数据。
- 本月目标是可面试展示的产品原型，不宣称已经达到可直接投入生产的企业级系统标准。
