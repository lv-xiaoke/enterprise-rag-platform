# 1. ORM 到底是什么？

你看到：

> ORM（对象关系映射）

很容易懵。

其实就是：

**让 Python 里的类，对应数据库里的表。**

比如数据库里面有一张表：

```text
users

id | name | age
---|------|----
1  | 张三 | 25
2  | 李四 | 26
```

如果不用 ORM，你可能需要直接写 SQL：

```sql
SELECT * FROM users;
```

用了 SQLAlchemy ORM 后，你可以用 Python 类表示这张表：

```python
class User:
    id
    name
    age
```

于是：

```text
Python                  PostgreSQL

User 类       ←→       users 表

id            ←→       id
name          ←→       name
age           ←→       age
```

所以：

> **ORM = 用 Python 对象的方式操作数据库，而不是到处手写 SQL。**

# 2. 什么是 Base？

你可能会看到：

```python
Base = declarative_base()
```

先不用管这行代码怎么实现。

你只需要记住：

比如 Day 4 你准备创建：

```python
class Organization(Base):
    ...

class Document(Base):
    ...

class KnowledgeBase(Base):
    ...
```

它们都继承：

```python
Base
```

也就是：

```text
                 Base
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
 Organization  Document  KnowledgeBase
```

所以今天创建 `Base`，是为了给 Day 4 铺路。

**今天不创建这些业务模型。**

# 3. Engine 是什么？

这是这一段最重要的概念之一。

你可以把：

```text
Engine
```

理解成：

> **数据库连接管理中心。**

比如你的 PostgreSQL 在：

```text
localhost:5432
```

你的 Python 程序想访问它。

SQLAlchemy 会创建：

```python
engine
```

大概相当于：

```text
你的 FastAPI
      ↓
   Engine
      ↓
 PostgreSQL
```

而 Engine 内部还会管理：

```text
数据库连接池
```

比如：

```text
Engine
 ├── 连接1
 ├── 连接2
 ├── 连接3
 ├── 连接4
 └── ...
```

所以为什么：

> **Engine 可以全局复用？**

因为它本来就是设计出来给整个应用管理数据库连接的。

你的整个 FastAPI 应用：

```text
FastAPI
   ↓
全局 Engine
   ↓
PostgreSQL
```

这是正常的。

# 4. 那 Session 又是什么？

Session 可以理解成：

> **一次具体的数据库办事过程。**

比如用户访问：

```http
POST /chat
```

这个请求需要查询数据库。

那么可以：

```text
用户请求
   ↓
创建 Session
   ↓
查询数据库
   ↓
完成操作
   ↓
关闭 Session
```

例如：

```python
db = SessionLocal()

# 查询数据库
...

db.close()
```

所以：

```text
Engine
= 数据库连接管理中心

Session
= 我这一次具体要操作数据库的工作单元
```

---

# 5. 为什么不能搞一个全局 Session？

这个非常重要。

假设你写：

```python
db = SessionLocal()
```

然后整个项目所有用户都使用这个 `db`。

假设同时来了：

```text
用户A
用户B
用户C
用户D
```

全部：

```text
        ↓
   一个 Session
   ↙ ↓ ↓ ↘
 A  B C  D
```

就容易出现：

- 数据互相影响
    
- 事务混乱
    
- Session 状态被污染
    
- 并发问题
    
- 出错后影响其他请求
    

正确方式是：

```text
用户A → Session A → 关闭
用户B → Session B → 关闭
用户C → Session C → 关闭
```

所以你要记：

> **Engine 是全局的，Session 是每次请求临时创建的。**

可以类比：

```text
Engine = 银行大厅
Session = 你这次办理业务的窗口/工作单

银行大厅可以一直存在
但你不能永远占着一个业务窗口
```

# 6. Alembic 是什么？

这个东西也特别容易懵。

假设今天你的数据库是：

```text
没有任何业务表
```

Day 4：

```text
创建 organization
```

Day 5：

```text
增加 organization.email
```

Day 6：

```text
创建 document
```

如果你直接手动修改数据库，很难知道：

> 谁什么时候改了什么？

所以 Alembic 就是：

> **数据库结构的 Git。**

Git 管理：

```text
代码变化
```

Alembic 管理：

```text
数据库结构变化
```

比如：

```text
版本 1
↓
没有业务表

版本 2
↓
创建 organization

版本 3
↓
创建 document

版本 4
↓
给 document 增加字段
```

这就是：

```text
Alembic Migration
```

# 8. FastAPI 生命周期是什么？

这个也简单。

你的 FastAPI 程序有两个重要时间：

```text
启动
 ↓
运行
 ↓

```

```text
startup
shutdown
```

```text

```

# 9. 为什么启动的时候执行 SELECT 1？

你可能看到：

```sql
SELECT 1;
```

这个 SQL 非常简单。

它基本相当于：

> **“PostgreSQL，你活着吗？我能不能连接你？”**

比如启动 FastAPI：

```text
FastAPI 启动
     ↓
连接 PostgreSQL
     ↓
SELECT 1
     ↓
成功？
```

如果成功：

```text
PostgreSQL 正常
↓
FastAPI 正常启动
```

如果失败：

```text
PostgreSQL 连不上
↓
FastAPI 启动失败
```

这有什么好处？

比如你忘了启动 Docker：

```text
PostgreSQL ❌
```

以前可能：

```text
FastAPI ✅
```

等你调用 `/chat`：

```text
突然报数据库错误 ❌
```

很难发现。

现在启动的时候直接告诉你：

```text
数据库连接失败
```

排查起来方便很多。

# 10. 退出的时候为什么要释放 Engine？

Engine 管理了很多数据库连接：

```text
Engine
 ├── connection 1
 ├── connection 2
 ├── connection 3
 └── connection 4
```

当 FastAPI 要关闭：

```text
FastAPI 退出
      ↓
关闭 Engine
      ↓
释放数据库连接
```

所以：

> **启动时建立/检查数据库资源，退出时释放数据库资源。**
