# Day 30：Mini RAG 项目模拟面试稿

## 一、30 秒项目概括

我用 FastAPI、DeepSeek API、BGE Embedding 和 FAISS 做了一个纯文本科研 PDF RAG 后端。系统支持上传 PDF，按页解析和切块后建立内存向量索引；用户提问时检索 Top-3 相关片段，再让大模型根据资料回答，并返回来源文本、页码和相似度。我还设计了 12 道固定问题评估检索与生成效果，并通过 Top-1 和 Top-3 对照分析参数选择。目前项目已完成本地运行、Dockerfile、README 和基础评估，但仍只支持单个文本型 PDF，索引也没有持久化。

## 二、3～5 分钟项目介绍

### 1. 项目动机与解决的问题

我本身是数学硕士，之前更熟悉深度学习和图像处理，但希望补齐 AI 应用开发中的后端工程能力，所以选择从零完成一个科研 PDF RAG 后端。这个项目主要解决两个问题：第一，大模型本身不知道用户刚上传的论文内容；第二，长文档如果整体放进 Prompt，不仅成本高，也很难精确找到与问题真正相关的部分。因此我的思路是先解析文档并建立可检索的知识库，提问时只把相关片段交给大模型，同时返回来源供用户核对。

### 2. 整体架构

后端使用 FastAPI 提供 HTTP 接口，并把职责拆分为 PDF 解析、文本切块、Embedding、向量检索、RAG 编排和 LLM 调用几个服务。整个系统分成上传和提问两条链路：上传阶段把 PDF 转换成带页码的向量索引；提问阶段先检索相关 Chunk，再构造 RAG Prompt 并调用 LLM。普通 `/chat` 与 RAG 问答相互独立，普通聊天历史写入 SQLite，`/rag/chat` 当前不保存聊天记录。

### 3. PDF 上传阶段

用户通过 `POST /upload` 上传带文字层的 PDF。项目使用 pypdf 按页提取文本，再按 200 个字符切块，相邻块保留 40 个字符 overlap，并为每个 Chunk 保存物理页码。之后使用 `BAAI/bge-small-zh-v1.5` 生成 512 维归一化向量，再写入 FAISS `IndexFlatIP`。FAISS 负责保存和搜索向量，Python 元数据列表负责保存原文和页码，两者通过相同的写入顺序建立对应关系。

上传过程还有一个简单的状态保护：只有 PDF 解析、切块、Embedding 和 FAISS 写入全部成功后，程序才会替换当前全局 RAG 服务。这样一次失败上传不会破坏上一份仍然可用的索引。

### 4. RAG 提问阶段

用户通过 `POST /rag/chat` 提问后，系统先使用同一个 BGE 模型生成问题向量，再从 FAISS 中检索 Top-3 Chunk。文档向量和问题向量都做了 L2 归一化，因此 `IndexFlatIP` 的内积可以作为余弦相似度排序。检索到的文本与用户问题会组成 RAG Prompt，其中明确要求资料没有答案时说明不知道。LLM 生成回答后，接口通过 Pydantic 模型返回 `answer` 和 `sources`，每条来源包含原文、页码和相似度。

这里的相似度只表示当前问题与 Chunk 的语义接近程度，用于结果排序，不是答案正确概率，也不是大模型置信度。

### 5. 关键工程设计

接口层主要负责请求校验、状态码和异常转换，具体能力放在 `services` 中。Pydantic 用于校验请求和响应，`httpx.AsyncClient` 用于异步等待 LLM API，配置通过环境变量读取，真实密钥不会写入代码。普通聊天记录使用 SQLite，项目还提供 Dockerfile，并通过 `.dockerignore` 排除 `.env`、虚拟环境和本地数据。

项目并不是所有操作都异步：Embedding、FAISS 和当前 SQLite 调用仍是同步操作。FastAPI 的异步路由主要让等待 LLM 网络请求时可以让出执行机会，不会自动加速本地模型计算。

### 6. 评估方法与结果

我针对一个三页测试 PDF 设计了 12 道固定问题，包括 6 道直接事实题、2 道总结题、2 道对比题和 2 道无答案题。我把检索和生成分开评估：先判断正确资料是否进入 Top-k，再人工检查最终回答是否覆盖标准答案并正确处理无答案问题。

基线参数是 `chunk_size=200`、`overlap=40`、`top_k=3`。10 道可回答题的检索都命中所需资料，12 道最终回答都通过人工检查。我还固定切块参数，单独比较 Top-1 和 Top-3：Top-1 命中 9/10，Top-3 命中 10/10。综合题 `summary-02` 需要跨 Chunk 整合 Embedding、检索和生成信息，因此从 Top-3 中获得了实际帮助，所以当前接口保留 Top-3。

这些结果只来自一个小型测试 PDF 和人工问题集，不能当作真实长论文上的通用准确率。它证明的是完整评估流程和参数对照已经跑通，而不是系统已经达到生产级效果。

### 7. 遇到的问题与解决方法

一个比较有代表性的问题是如何让来源元数据贯穿整条检索链路。最初只返回文本比较简单，但为了展示页码和相似度，必须保证 Chunk 元数据不会在 Embedding 和 FAISS 搜索过程中丢失。

我的处理方式是定义 `DocumentChunk` 保存文本和页码，定义 `SearchResult` 保存文本、页码和分数，并让 FAISS 中的向量编号与元数据列表保持相同写入顺序。检索得到向量编号后，程序就能找回完整来源，再通过 `RAGSource` 返回给客户端。这个过程让我理解了向量索引和业务元数据是两套数据，实际系统必须为它们建立稳定映射。

另一个问题是 Top-k 不能凭感觉决定。我通过固定问题集比较 Top-1 和 Top-3，找到了综合题需要额外来源的具体案例，因此选择 Top-3 时有真实数据依据，而不是直接照搬常见默认值。

### 8. 已知限制与后续优化

当前项目只支持带文字层的 PDF，不支持扫描件 OCR、图片、复杂表格和多模态内容。系统只保存最近一次成功上传的内存 FAISS 索引，不支持多文档 ID、用户隔离和索引持久化，服务重启后需要重新上传。当前也没有完整的自动化测试、身份认证、限流和正式生产部署配置，评估只覆盖一个三页 PDF。

下一步我会优先增加索引持久化和多文档管理，并使用更长的真实论文扩大问题集，继续比较 Chunk、overlap 和 Top-k。然后补充关键服务与接口的自动化测试、认证和资源限制。只有评估数据证明有需要时，我才会考虑增加 BM25、Reranker 等组件，而不是先堆叠尚未验证的框架。

## 三、常见追问与回答

### 1. 为什么使用 FastAPI？

FastAPI 能把 Python 类型注解、Pydantic 校验、OpenAPI 文档和异步接口结合起来，适合快速构建 AI 应用后端。当前项目用它实现普通聊天、历史记录、PDF 上传和 RAG 问答等接口。它可以减少接口层样板代码，但不会自动做好业务分层，也不会让同步的 Embedding 和 FAISS 自动变成异步。

### 2. 为什么选择 BGE-small-zh？

当前项目面向中文 PDF，`BAAI/bge-small-zh-v1.5` 能生成中文语义向量，模型规模也适合本地学习和验证。项目还按照模型使用方式给查询增加指令，并分别编码问题和文档。这个选择只经过当前小型问题集验证，真实业务仍应与其他候选模型比较检索质量、速度和资源占用。

### 3. 为什么归一化后使用 IndexFlatIP？

文档向量和查询向量都做 L2 归一化后，两个向量的内积等于它们的余弦相似度，因此可以使用 FAISS `IndexFlatIP` 排序。`IndexFlatIP` 是精确搜索，逻辑简单，适合当前很小的索引。数据规模扩大后，它的搜索成本会随向量数量增加，届时才需要评估近似索引。

### 4. Chunk 为什么是 200，overlap 为什么是 40？

Chunk 太大会混合多个主题，太小会切断语义，overlap 用于降低关键信息落在边界上的风险。当前的 200 和 40 是针对三页测试 PDF 建立的基线，不是通用最优参数。真实论文需要使用更大、更有代表性的问题集比较检索命中、回答质量、上下文长度和成本。

### 5. 为什么选择 Top-3？

固定切块参数后，Top-1 在 10 道可回答题中命中 9 道，Top-3 命中 10 道。综合题 `summary-02` 需要多个 Chunk 才能覆盖完整流程，因此 Top-3 有实际收益。继续增大 k 可能带来噪声、重复内容和更长 Prompt，所以不能认为越大越好。

### 6. 怎样区分检索错误和生成错误？

先检查标准答案需要的内容是否进入 Top-k。如果正确 Chunk 没进入 Top-k，主要检查文档解析、Chunk、Embedding 和检索参数；如果正确 Chunk 已经进入 Top-k，但最终回答仍错误，则主要检查 Prompt、上下文组织和 LLM 生成。当前评估分别记录 `retrieval_hit` 和 `answer_correct`，就是为了拆开这两类问题。

### 7. 怎样减少幻觉？

当前项目使用外部 PDF、Top-3 检索和无答案约束，并返回原文、页码和相似度供人工核对。还可以继续提高解析和检索质量、过滤低相关资料，并对关键结论做规则或人工校验。RAG 只能减少一部分知识型幻觉；如果检索错误或模型忽略资料，仍然可能产生错误回答。

### 8. 项目为什么不是 Agent？

当前上传、切块、Embedding、检索、构造 Prompt 和生成都按 Python 代码规定的固定顺序执行，所以它是 RAG Workflow。LLM 不能自行决定是否检索、改变查询、选择其他工具或循环执行，因此不属于 Agent。固定 Workflow 更容易控制、测试和评估，当前需求也不需要为了使用 Agent 而增加复杂度。

### 9. 多个用户同时上传 PDF 会怎样？

当前进程中只有一个全局 RAG 服务，后一次成功上传会覆盖前一次索引，因此不支持用户隔离。这是学习版项目为了先跑通单文档链路做的范围控制。下一步需要给文档分配 ID，持久化索引和元数据，并让查询明确指定文档或知识库，同时增加权限校验。

### 10. 服务重启后索引还在吗？

不在。当前 FAISS 索引只保存在进程内存中，服务重启后需要重新上传 PDF。后续可以保存 FAISS 索引、Chunk 元数据和文档信息，并在启动时按文档 ID 加载，但还需要处理版本、删除和一致性问题。

### 11. 为什么没有使用 BM25 或 Reranker？

当前目标是先完整跑通纯向量 RAG 链路，并通过评估定位真实问题。现有小型问题集已经能够验证 Embedding、FAISS 和 Top-k 的作用，还没有证据表明增加组件的收益足以抵消复杂度和延迟。后续在真实论文中发现专有名词匹配或排序问题后，再分别评估 BM25 和 Reranker。

### 12. 如果用于真实长论文，下一步先改什么？

我会先扩大评估集，而不是直接更换框架：选择多篇真实论文，增加事实、总结、跨段落和无答案问题，再比较不同 Chunk、overlap 和 Top-k。工程上优先增加索引持久化、多文档管理和自动化测试。拿到更可靠的失败案例后，再决定是否加入结构化切块、BM25 或 Reranker。

## 四、简历项目表述

### 一句话版本

基于 FastAPI、LLM API、BGE Embedding 和 FAISS 构建科研 PDF RAG 问答后端，实现文档解析、重叠切块、向量检索、来源页码返回及 Docker 容器化；设计 12 道固定问题评估检索与生成效果，并通过 Top-1/Top-3 对照分析检索参数。

### 两条要点版本

- 基于 FastAPI、DeepSeek API、BGE Embedding 和 FAISS 实现科研 PDF RAG 后端，完成按页解析、字符切块、Top-3 向量检索及带页码和相似度的来源返回。
- 设计 12 道固定问题区分检索命中与回答正确，并在固定切块参数下完成 Top-1/Top-3 对照，检索命中由 9/10 提升至 10/10。

### 表述边界

当前项目没有达到生产级高并发，不支持任意复杂 PDF，也没有彻底解决幻觉或证明通用准确率达到 100%。面试和简历中的每一项能力都应当能在代码、README 或评估 JSON 中找到证据。
