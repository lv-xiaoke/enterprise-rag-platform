因为 Python 需要把“**描述一个异步任务**”和“**真正执行这个任务**”分开。

这个中间的 coroutine 对象，本质上就是：

> **一个尚未执行完成的异步任务描述。**

如果没有这个中间态，Python 就很难决定：这个异步函数应该什么时候执行、由谁等待、怎么和其他任务一起调度。

比如：

```python
async def get_data():
    print("开始请求")
    return "hello"
```

当你写：

```python
coro = get_data()
```

此时 Python 先得到：

```text
coro
↓
coroutine 对象
↓
“以后要执行 get_data()”
```

但还没有真正开始跑。

然后你可以决定怎么处理它：

```python
result = await coro
```

也可以把多个协程一起交给事件循环：

```python
await asyncio.gather(
    task1(),
    task2(),
    task3(),
)
```

这里就能看出 coroutine 对象的价值了。

如果 `task1()`、`task2()`、`task3()` 一调用就立刻从头执行到底，那么 Python 很难先把这三个任务“收集起来”，再统一调度。

有了 coroutine 对象以后，相当于先创建三张任务单：

```text
task1() → 协程对象 A
task2() → 协程对象 B
task3() → 协程对象 C

           ↓

      交给事件循环

           ↓

决定：
A 跑一会儿
A 遇到 await
↓
切到 B

B 遇到 await
↓
切到 C

C 遇到 await
↓
再看谁已经准备好了
```

所以这个“中间态”实际上是异步调度的基础。

你可以把普通函数和异步函数这样对比。

普通函数：

```python
result = func()
```

意思基本是：

```text
现在执行
↓
一直执行
↓
拿到结果
```

异步函数：

```python
coro = func()
```

更像：

```text
先创建一个“可执行流程”
↓
暂时不要求立刻完成
↓
以后交给 await / 事件循环
```

然后：

```python
result = await coro
```

才是：

```text
开始/继续执行这个流程
↓
中间如果需要等待，可以暂停
↓
等待期间运行其他任务
↓
最后拿到结果
```

还有一个更直观的比喻：**普通函数像“现场办业务”，协程对象像“取号单”。**

普通函数：

```text
你去窗口
↓
工作人员马上开始办
↓
你一直在窗口等
↓
办完拿结果
```

协程：

```text
get_data()
↓
先拿到一张取号单（coroutine）
↓
事件循环决定什么时候处理
↓
处理过程中遇到等待
↓
暂时挂起
↓
去处理其他人的号码
↓
你的数据到了
↓
回来继续
```

所以 coroutine 对象并不是一个“多余步骤”，反而是为了让 Python 能做到三件重要的事：

1. **延迟执行**：调用异步函数时，不必马上从头跑到底。
    
2. **统一调度**：事件循环可以管理很多协程。
    
3. **暂停和恢复**：协程遇到 `await` 可以保存当前状态，之后再从原位置继续。
    

你甚至可以把：

```python
coro = get_data()
```

理解成：

```text
“我创建了一个未来可以运行的 get_data 流程。”
```

而：

```python
await coro
```

理解成：

```text
“现在把这个流程交给异步系统执行，我要它最终的结果。”
```

所以最核心的一句话是：

> **协程对象存在，是因为异步编程需要把“创建任务”和“执行/等待任务”分开，这样事件循环才有机会调度多个任务。**

这也是为什么 `async def` 的调用行为和普通 `def` 故意设计得不一样。
