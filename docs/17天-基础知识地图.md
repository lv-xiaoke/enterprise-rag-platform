# 一、先理解：这个项目最终是什么

这个项目最终不是一个“调用大模型 API 的聊天程序”，而是一个：

> **可以管理多个企业知识库、上传多份 PDF、持久化保存文档和向量、进行语义检索，并基于检索结果回答问题的后端系统。**

例如企业中可能存在：

```text
知识库：人事制度
├── 员工请假制度.pdf
├── 考勤管理办法.pdf
└── 员工福利制度.pdf

知识库：财务制度
├── 差旅报销制度.pdf
├── 发票管理办法.pdf
└── 采购审批制度.pdf
```

用户可以：

```text
创建知识库
    ↓
上传 PDF
    ↓
系统解析 PDF
    ↓
切分 Chunk
    ↓
生成 Embedding
    ↓
保存进 PostgreSQL + pgvector
    ↓
用户提出问题
    ↓
从指定知识库检索相关 Chunk
    ↓
把 Chunk 交给 LLM
    ↓
生成带来源的回答
```

这就是整个项目最重要的一条主线。

---

# 二、先记住系统的两条核心链路

整个项目虽然有很多技术名词，但最重要的其实只有两条链路。

## 链路一：文档入库

```text
PDF
 ↓
上传 API
 ↓
创建 Document 记录
 ↓
读取 PDF
 ↓
提取文本
 ↓
切分 Chunk
 ↓
Embedding
 ↓
生成 512 维向量
 ↓
Chunk + Vector 写入 PostgreSQL
```

这条链路解决的是：

> 企业资料怎样变成可以被搜索的数据？

---

## 链路二：用户问答

```text
用户问题
 ↓
生成 Query Embedding
 ↓
pgvector 相似度搜索
 ↓
Top-K Chunk
 ↓
过滤知识库 / 文档状态
 ↓
构造 Context
 ↓
LLM
 ↓
回答
 ↓
返回来源、页码、Chunk、分数
```

这条链路解决的是：

> 用户的问题怎样找到正确资料，并基于资料回答？

以后学习任何技术，都先问自己：

```text
它属于文档入库链路？

还是属于问答链路？

还是属于支撑两条链路运行的基础设施？
```

# 四、数据库到底解决什么问题

原来的 RAG Demo 很可能使用：

```text
Python 内存
+
FAISS
+
SQLite
```

这种方式适合学习，但存在明显问题。

例如程序重启：

```text
内存中的对象
↓
全部消失
```

FAISS 如果没有专门保存：

```text
向量索引
↓
也会消失
```

而真正的企业应用需要：

```text
今天上传 PDF

关闭程序

明天重新启动

PDF、Chunk、Embedding 仍然存在
```

这就是为什么需要数据库。

# 五、PostgreSQL 是什么

PostgreSQL 可以先理解成：

> 一个负责长期保存结构化数据的数据库服务器。

例如我们可以保存：

```text
KnowledgeBase
Document
Chunk
```

对应数据库里的三张表。

大致可能是：

```text
knowledge_bases

documents

chunks
```

例如：

```text
knowledge_bases

id | name
---|---------
1  | 人事制度
2  | 财务制度
```

Document：

```text
id | knowledge_base_id | filename | status
---|-------------------|----------|--------
1  | 1                 | 请假制度 | ready
2  | 1                 | 考勤制度 | ready
```

Chunk：

```text
id | document_id | page | content
---|-------------|------|--------
1  | 1           | 2    | 员工请假需要……
2  | 1           | 3    | 年假申请需要……
```

# 八、什么是主键和外键

## 1. 主键 Primary Key

每条数据需要唯一身份。

例如：

```text
Document

id = 17
```

这里的：

```text
id
```

就是主键。

即使两个文件都叫：

```text
员工手册.pdf
```

它们仍然可以通过不同 id 区分。

---

## 2. 外键 Foreign Key

外键用于描述数据之间的关系。

例如 Document：

```text
id = 10

knowledge_base_id = 3
```

表示：

```text
Document 10
属于
KnowledgeBase 3
```

所以：

```text
knowledge_base_id
```

就是外键。

# 九、SQL 是什么

数据库并不是直接理解 Python。

数据库理解的是 SQL，例如：

```sql
SELECT * FROM documents;
```

表示：

```text
查询 documents 表里的数据
```

插入数据：

```sql
INSERT INTO documents (...)
VALUES (...);
```

但是如果整个 Python 项目到处手写 SQL：

```text
API
↓
手写 SQL

Service
↓
手写 SQL

各种地方
↓
手写 SQL
```

代码会越来越难管理。

于是出现 ORM。

# 十、ORM 是什么

ORM：

```text
Object Relational Mapping
```

即：

```text
对象关系映射
```

可以先理解成：

> 让 Python 对象和数据库表之间建立对应关系。

例如原本 SQL：

```sql
SELECT * FROM documents WHERE id = 1;
```

通过 ORM 后，可能写成：

```python
session.get(Document, 1)
```

你操作的是：

```text
Python 对象
```

ORM 帮你转换为：

```text
SQL
```

最终还是 PostgreSQL 在执行 SQL。

因此完整链路是：

```text
Python
↓
SQLAlchemy ORM
↓
SQL
↓
PostgreSQL
```

# 十一、SQLAlchemy 是什么

SQLAlchemy 是 Python 中非常常见的数据库工具。

这个项目主要使用它完成三件事情。

## 1. 定义 Model

例如：

```text
KnowledgeBase
Document
Chunk
```

---

## 2. 建立数据库连接

例如：

```text
FastAPI
↓
SQLAlchemy Engine
↓
PostgreSQL
```

---

## 3. 操作数据库

例如：

```text
创建知识库

查询 Document

保存 Chunk
```

因此不要把 SQLAlchemy 理解成数据库。

正确关系是：

```text
SQLAlchemy
=
Python 操作数据库的工具

PostgreSQL
=
真正保存数据的数据库
```

# 十二、psycopg 是什么

SQLAlchemy 自己不会直接和 PostgreSQL 网络通信。

中间还需要一个 PostgreSQL Driver：

```text
psycopg
```

关系可以理解成：

```text
Python 代码
   ↓
SQLAlchemy
   ↓
psycopg
   ↓
PostgreSQL
```

其中：

```text
SQLAlchemy
```

负责提供比较高级的数据库操作方式。

```text
psycopg
```

负责真正和 PostgreSQL 通信。

# 十三、Engine 是什么

SQLAlchemy 中：

```text
Engine
```

可以先理解为：

> 应用连接数据库的总入口。

例如：

```text
FastAPI
 ↓
Engine
 ↓
PostgreSQL
```

Engine 内部会维护：

```text
数据库连接
连接池
连接配置
```

通常：

```text
一个应用创建一个 Engine
```

然后整个应用复用。

**连接池（Connection Pool）**，你可以先把它理解成：

> **提前准备好一批数据库连接，大家轮流借来用，而不是每次访问数据库都重新建立连接。**

放到你现在学的 SQLAlchemy + PostgreSQL 里，很重要。

假设你的 FastAPI 接口收到一次请求，要查 PostgreSQL。如果**没有连接池**，可能是：

```text
收到请求
↓
和 PostgreSQL 建立连接
↓
执行 SQL
↓
关闭连接
```

下一个请求又重新来一遍。

问题是：**建立数据库连接本身是有成本的**，包括网络连接、认证、初始化等。如果接口请求很多，反复建立和关闭连接会浪费时间。

所以一般会使用连接池：

```text
                 连接池
        ┌───────────────────┐
        │ Connection 1      │
        │ Connection 2      │
        │ Connection 3      │
        │ Connection 4      │
        └───────────────────┘
              ↑        ↓
FastAPI 请求 ─┘        └─ 使用完归还
```

比如请求 A 来了：

```text
连接池
↓
借出 Connection 1
↓
执行 SQL
↓
不是关闭连接
↓
而是把 Connection 1 还给连接池
```

之后请求 B 可以继续使用它。

### 和你现在的 SQLAlchemy 代码是什么关系？

你现在可能有：

```python
engine = create_engine(
    database_url,
    pool_pre_ping=True,
)
```

这里的：

```python
engine
```

不应该简单理解成“一个数据库连接”。

更准确地说：

> **Engine 是 SQLAlchemy 管理数据库连接的重要入口，其中包含连接池。**

可以理解成：

```text
Engine
│
├── 数据库地址
├── PostgreSQL 驱动 psycopg
├── 连接池 Pool
│   ├── Connection 1
│   ├── Connection 2
│   └── Connection 3
│
└── SQL 执行相关功能
```

所以之前说：

> Engine 可以全局复用

一个重要原因就是：

> **它负责统一管理连接池。**

而不是每次 API 请求都创建一个新的 Engine。

---

再区分一个非常容易混淆的概念：

```text
Engine
↓
管理连接池

Connection
↓
真正连接 PostgreSQL 的数据库连接

Session
↓
你进行一组 ORM / 数据库操作的工作单元
```

例如：

```python
session = SessionLocal()

user = session.query(User).first()

session.close()
```

这里 `session.close()` 很多时候并不是：

> “彻底把 PostgreSQL TCP 连接销毁掉。”

而更像：

> **Session 用完了，把它占用的数据库连接归还给连接池。**

于是下一次请求还能复用这个连接。

你可以用一个餐厅类比记住：

```text
PostgreSQL        = 厨房

Connection        = 厨房和服务员之间的传菜通道

连接池            = 已经准备好的多条传菜通道

Engine            = 管理这些通道的经理

Session           = 某一桌客人的这一轮点餐过程
```

所以为什么不能搞一个全局 Session 给所有 FastAPI 请求一起用？

因为：

```text
请求 A
请求 B
请求 C
```

可能同时操作数据库，如果所有人共享同一个 Session，事务状态、查询状态就可能互相影响。

更合理的是：

```text
全局：
Engine + 连接池

每个请求：
创建自己的 Session
↓
执行数据库操作
↓
关闭 Session
↓
连接归还连接池
```

你现在阶段可以先牢牢记住一句话：

> **连接池 = 保存并复用数据库连接的池子，避免每次请求都重新连接 PostgreSQL。**

以及：

> **Engine 通常长期存在并管理连接池，Session 通常按一次请求创建和关闭。**

# 十四、Session 是什么

Session 可以先理解成：

> 一次数据库操作过程中的工作区。

例如一个 API 请求：

```text
POST /knowledge-bases
```

可能执行：

```text
创建 Session

↓

INSERT KnowledgeBase

↓

commit

↓

关闭 Session
```

所以：

```text
Engine
```

是整个应用长期存在的数据库入口。

而：

```text
Session
```

通常服务于一次具体业务操作。

不要让所有请求共享同一个长期 Session。

# 十五、事务 Transaction 是什么

假设上传 PDF 时需要执行：

```text
创建 Document

创建 Chunk 1

创建 Chunk 2

创建 Chunk 3
```

如果：

```text
Chunk 2 写入失败
```

你可能不希望数据库留下一个半成品：

```text
Document 有了

Chunk 只保存了一半
```

事务解决的就是：

> 一组操作要么全部成功，要么全部失败。

例如：

```text
BEGIN

创建 Document
创建 Chunk
创建 Chunk
创建 Chunk

COMMIT
```

如果中间出错：

```text
ROLLBACK
```

数据库恢复到操作开始之前。

Day 8 中的：

```text
完善事务和失败状态
```

主要就是在解决这种问题。

# 十六、Alembic 是什么

现在假设第一次设计数据库：

```text
knowledge_bases
documents
chunks
```

过几天发现 Document 需要增加：

```text
file_size
```

你不能每次都：

```text
删除数据库
重新建数据库
```

因为真实系统中已经有数据了。

Alembic 的作用就是：

> 管理数据库结构如何从版本 A 变化到版本 B。

例如：

```text
Migration 001
创建 knowledge_bases

Migration 002
创建 documents

Migration 003
增加 documents.file_size
```

于是数据库结构拥有历史。

# 十七、为什么不能只用 Base.metadata.create_all()

SQLAlchemy 可以通过：

```text
create_all()
```

直接创建表。

但它更适合：

```text
简单测试
Demo
```

真实项目更希望知道：

```text
数据库经历了哪些修改？
```

例如：

```text
版本 1
↓
版本 2
↓
版本 3
```

Alembic 可以：

```text
upgrade
```

升级数据库。

也可以：

```text
downgrade
```

回滚数据库。

因此 Day 1 才要求：

```text
迁移可以升级、回滚、再次升级
```

这实际上是在验证：

> 数据库版本管理机制已经建立。

# 十八、pgvector 是什么

PostgreSQL 本身非常擅长保存：

```text
字符串
整数
时间
JSON
```

但是 RAG 还需要保存：

```text
Embedding Vector
```

例如：

```text
[
0.12,
-0.35,
0.98,
...
]
```

一共有：

```text
512 维
```

pgvector 是 PostgreSQL 的一个扩展。

它让 PostgreSQL 能够理解：

```text
vector
```

这种数据类型，并执行：

```text
向量相似度搜索
```

所以：

```text
PostgreSQL
+
pgvector
```

就可以同时保存：

```text
Document 信息
Chunk 文本
Chunk 页码
Embedding 向量
```

---

# 十九、为什么从 FAISS 改成 pgvector

原来的结构可能是：

```text
SQLite
负责文档信息

FAISS
负责向量
```

这样存在一个问题：

```text
数据分散在两个地方
```

例如：

```text
FAISS 返回 index = 27
```

你还需要知道：

```text
27 对应哪份 PDF？
哪一页？
哪个 Chunk？
属于哪个知识库？
```

而使用 PostgreSQL + pgvector，可以让：

```text
文本
页码
document_id
knowledge_base_id
embedding
```

存在同一个数据库体系中。

检索时就可以直接：

```text
WHERE knowledge_base_id = 3

AND document.status = 'ready'

ORDER BY embedding 相似度
```

这也是 Day 5 为什么特别强调：

```text
按知识库和文档状态过滤
```

# 二十、Embedding 是什么

Embedding 可以先理解成：

> 把文本转换为一串数字，让计算机可以比较文本语义。

例如：

```text
员工如何申请年假？
```

转换成：

```text
[0.17, -0.28, ...]
```

而 Chunk：

```text
员工申请年假需提前三个工作日提交审批
```

也转换成一个向量。

如果它们意思接近：

```text
两个向量距离较近
```

于是就可以完成语义搜索。

---

# 二十一、为什么是 512 维

你当前使用的 Embedding 模型输出：

```text
512 维向量
```

可以简单理解成：

```text
每段文本
↓
变成 512 个数字
```

例如实际不是：

```text
[0.1, 0.2, 0.3]
```

这么短，而是：

```text
[
数字1,
数字2,
数字3,
...
数字512
]
```

因此数据库里的向量字段也必须定义为：

```text
vector(512)
```

如果数据库要求：

```text
512
```

而模型输出：

```text
768
```

就无法直接写进去。

---

# 二十二、Chunk 是什么

LLM 和 Embedding 通常不会把整本 PDF 当成一个检索单元。

例如一份：

```text
30 页员工手册
```

如果整体生成一个 Embedding：

```text
一个问题只能匹配整本书
```

无法知道答案具体在哪里。

所以需要切成：

```text
Chunk 1
Chunk 2
Chunk 3
...
```

例如：

```text
Chunk 17

page = 8

content =
员工年假需要提前三个工作日申请……
```

这样用户问：

```text
年假怎么申请？
```

系统就可能找到 Chunk 17。

---

# 二十三、为什么 Chunk 必须保存页码

因为企业 RAG 不能只说：

```text
答案是……
```

还应该告诉用户：

```text
答案来自哪里？
```

例如：

```text
《员工请假制度》
第 8 页

员工年假需要提前三个工作日申请……
```

所以文档处理时就必须保存：

```text
document_id

page

content

embedding
```

而不能最后回答时才想办法找来源。

---

# 二十四、Top-K 是什么

假设数据库里有：

```text
10000 个 Chunk
```

用户提出问题后，系统不会把 10000 个 Chunk 全部交给 LLM。

而是搜索最相关的几个。

例如：

```text

```

就是：

```text
最相关 Chunk 1

最相关 Chunk 2

最相关 Chunk 3
```

Top-K 中的：

```text
K
```

表示返回几个结果。

例如：

```text
Top-1

Top-3

Top-5
```

> K 取不同值时，正确证据被找回来的概率如何变化？

# 三十、RAG 到底是什么

RAG：

```text
Retrieval-Augmented Generation
```

核心不是“让模型拥有数据库”。

而是：

```text
用户问题

↓

检索相关资料

↓

把资料放进 Prompt

↓

让 LLM 基于资料回答
```

例如：

```text
Question：

员工年假怎么申请？
```

系统先找到：

```text
Context：

《员工请假制度》第 8 页：
员工年假需提前三个工作日……
```

然后构造 Prompt：

```text
请根据以下资料回答问题。

资料：
员工年假需提前三个工作日……

问题：
员工年假怎么申请？
```

LLM 才生成回答。

# 三十一、为什么需要拒答

如果数据库里没有答案，例如用户问：

```text
公司的股票期权制度是什么？
```

但你的知识库只有：

```text
请假制度
报销制度
考勤制度
```

系统不应该强行回答。

应该返回类似：

```text
当前知识库中没有找到足够的信息。
```

这就是：

```text
拒答
```

企业 RAG 中这是非常重要的能力。

因为：

```text
不知道
```

通常比：

```text
编一个答案
```

更加可靠。

---

# 三十二、为什么需要检索阈值

即使完全不相关的问题，向量数据库通常还是可以返回：

```text
Top-K
```

只是这些结果相似度很低。

所以可以设置：

```text
similarity threshold
```

例如：

```text
score < threshold
```

认为：

```text
没有可靠证据
```

于是执行拒答。

---

# 三十三、Recall@K 是什么

假设问题：

```text
员工年假需要提前多久申请？
```

我们提前人工标注正确证据：

```text
Chunk 17
```

系统检索 Top-3：

```text
Chunk 5

Chunk 17

Chunk 26
```

那么正确 Chunk 出现在前三名。

于是：

```text
Recall@3 = 命中
```

如果很多测试题中：

```text
100 道题

其中 85 道正确证据出现在 Top-3
```

那么：

```text
Recall@3 = 85%
```

---

# 三十四、MRR 是什么

Recall 主要关心：

```text
正确答案有没有出现？
```

MRR 还关心：

```text
出现得够不够靠前？
```

例如：

情况 A：

```text
正确 Chunk 排第 1
```

情况 B：

```text
正确 Chunk 排第 5
```

虽然两个都可能：

```text
Recall@5 = 命中
```

但显然：

```text
排第 1
```

更好。

MRR 就是评价这种排名质量。

# 三十九、整个项目最终应该能够解释成这一分钟版本

面试时可以逐渐练习把项目讲成：

> 我做的是一个企业制度与 SOP 智能知识库。
> 
> 用户首先创建知识库并上传 PDF，后端使用 FastAPI 接收文件，通过 PDF 解析和 Chunk 切分得到文本块，再使用 Embedding 模型生成 512 维向量。
> 
> 文档元数据、Chunk、页码和 Embedding 都持久化到 PostgreSQL，其中向量使用 pgvector 保存。
> 
> 用户提问以后，我会先生成 Query Embedding，然后在指定知识库中通过 pgvector 做 Top-K 相似度检索，并过滤未处理完成的 Document。
> 
> 检索结果会作为 Context 交给 LLM，并在最终回答中返回文档名、页码、原文 Chunk 和检索分数。
> 
> 对于没有足够证据的问题，通过检索阈值进行拒答。
> 
> 同时我建立了一套固定评测集，通过 Recall@K、MRR、拒答正确率和检索延迟评估系统，并使用 pytest 覆盖核心检索逻辑。

如果这段话完全理解，就说明已经掌握整个项目主线。
