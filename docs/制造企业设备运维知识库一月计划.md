# 制造企业设备运维知识库：一个月项目与 B 站教学计划

## 一、这个月要完成什么

在现有 Mini RAG 后端的基础上，制作一个虚构但业务链路完整的“制造企业设备运维知识库”。项目使用公开、非敏感、来源可追溯的参考资料，以及自己编写的虚构企业数据，不使用任何真实企业的内部资料、人员信息、设备序列号或维修记录。

虚构企业暂定为：

> **启明精工设备有限公司**：一家拥有机加工与装配产线的中小型制造企业，需要统一管理设备档案、操作规程、点检标准、故障处理、保养计划和历史维修案例。

员工可以向知识库提问：

- “空压机排气温度过高应该先检查什么？”
- “输送带每天开机前需要检查哪些项目？”
- “3 号离心泵最近发生过哪些重复故障？”
- “CNC 主轴异响时有哪些必须停机的情况？”
- “这条回答依据的是哪份文档、哪个版本和哪一页？”

月底最终交付物包括：

1. 一套虚构但结构完整的制造企业设备运维资料集。
2. 一个支持多文档、持久化、版本管理和来源引用的 RAG 后端。
3. 一个可直接演示的轻量问答与文档管理页面。
4. 一套不少于 50 道问题的 RAG 评测集及评测报告。
5. 完整 README、架构图、数据说明、演示脚本和案例报告。
6. 8 条阶段教学视频和 1 条最终项目演示视频。

计划周期为 30 天，每天 2 小时，总投入约 60 小时。其中前四周各 14 小时，最后两天 4 小时用于补漏、发布和复盘。

## 二、项目范围与取舍

### 本月必须完成

- PostgreSQL + pgvector 保存知识库、文档、Chunk、向量和业务元数据。
- 支持一个知识库内的多文档检索，服务重启后数据不丢失。
- 支持文档上传、列表、处理状态、停用和重新索引。
- 文档具有设备类型、文档类型、版本、生效日期等元数据。
- 回答引用精确到文档名称、版本、页码和 Chunk。
- 资料不足时明确拒答，不编造维修步骤。
- 建立可重复执行的评测集，比较至少两组检索参数。
- 提供一个轻量演示页面，使非技术人员也能看懂效果。
- Docker Compose 能启动主要依赖，README 能指导他人复现。

### 有余力再完成

- PostgreSQL 全文检索与向量检索组成混合检索。
- 增加 Reranker、相邻 Chunk 合并和检索阈值调优。
- `admin`、`engineer`、`viewer` 三种演示角色及简单权限过滤。
- 后台异步处理和失败重试；可先用 FastAPI 后台任务，不强制引入 Celery。
- 简单的问答反馈、检索耗时和未回答问题统计。

### 本月暂不做

- 不接入真实工厂设备或生产系统。
- 不做自动下发维修指令、自动控制设备等高风险 Agent 功能。
- 不把 Kubernetes、复杂微服务、完整多租户和商业级前端作为本月目标。
- 不强行支持扫描件、复杂表格和图片理解；OCR 只作为后续扩展。
- 不因追求功能数量而跳过数据来源、评测和可复现文档。

这套取舍的目标是做出一条真正可运行、可解释、可评测、可演示的完整链路，而不是在一个月内堆出大量未经验证的框架。

## 三、虚构知识库的内容设计

### 1. 设备范围

第一版只覆盖四类常见设备，既能体现跨设备检索，又不会让资料制作失控：

|设备类型|虚构资产示例|主要知识主题|
|---|---|---|
|螺杆式空气压缩机|AC-01、AC-02|高温、压力不足、滤芯、润滑、日常点检|
|离心泵|P-01、P-02、P-03|汽蚀、泄漏、振动、密封、启停流程|
|皮带输送机|CV-01、CV-02|跑偏、打滑、异响、张紧、急停检查|
|数控机床|CNC-01、CNC-02|主轴、润滑、报警、精度、停机条件|

### 2. 资料集组成

资料不必伪装成某家真实公司的文件，而要统一标明“教学演示用虚构数据”。建议制作：

| 资料类型      |    目标数量 | 内容                     |
| --------- | ------: | ---------------------- |
| 企业与部门说明   |     1 份 | 企业背景、设备部职责、角色说明        |
| 设备台账      |     1 份 | 9 台虚构设备的编号、位置、投用日期、状态  |
| 安全与通用制度   |     2 份 | 停送电、挂牌上锁、异常停机与上报规则     |
| 操作与点检 SOP |     8 份 | 每类设备各 1 份操作规程和 1 份点检规程 |
| 故障诊断指南    |     4 份 | 每类设备的症状、可能原因、检查顺序和升级条件 |
| 保养计划      |     4 份 | 日、周、月、季度保养项目及责任角色      |
| 备件与耗材目录   |     1 份 | 虚构料号、适用设备和安全库存         |
| 维修工单      | 30～50 条 | 时间、设备、现象、原因、措施、停机时长和复盘 |
| 版本变更通知    |     2 份 | 制造新旧版本冲突，用于验证版本过滤      |

最终形成约 20～25 份可入库文档、30～50 条结构化工单。自己编写的 Markdown、CSV 可以转换为带页码的 PDF 作为第一版入库文件，原始文件继续保留，便于将来增加多格式解析。

### 3. 公开资料使用原则

“网上公开可下载”不等于“可以随意复制和重新发布”。本项目按以下规则处理：

- 优先参考政府部门公开的安全生产指南、设备厂商公开手册、开放课程资料和具有明确开放许可的内容。
- 为每个来源登记标题、发布机构、URL、访问日期、许可或使用说明、采用了哪些知识点。
- 不复制真实企业名称、Logo、联系方式、设备序列号、客户信息或维修记录。
- 不大段照抄标准和厂商手册；将公开知识重新整理成自己编写的教学 SOP，并保留来源说明。
- 没有明确再分发许可的原始文件只用于本地研究，不提交到公开仓库；仓库仅提交来源清单、自己编写的资料和生成脚本。
- 所有虚构工单、人员、资产编号和业务数据都明确标注为 synthetic / demo。
- 维修建议必须包含“断电、泄压、挂牌上锁、由有资质人员处理”等必要边界，系统定位为知识查询工具，不替代现场安全规程和专业判断。

建议建立 `source_registry.csv`，至少包含以下字段：

```text
source_id,title,publisher,url,accessed_at,license_or_terms,used_for,redistributable,notes
```

### 4. 文档元数据

每份入库文档至少保留：

```text
knowledge_base_id
document_id
title
document_type
equipment_type
equipment_ids
version
effective_date
status
source_type
page
chunk_id
```

其中 `status` 至少区分 `draft`、`active`、`inactive`。检索默认只允许使用 `active` 版本，防止旧规程继续参与回答。

## 四、整体实施路线

```mermaid
flowchart LR
    A["公开资料与来源登记"] --> B["虚构企业资料集"]
    B --> C["多文档解析与持久化"]
    C --> D["检索、引用与拒答"]
    D --> E["固定问题集评测"]
    E --> F["轻量演示界面"]
    F --> G["README、案例报告与 B 站视频"]
```

路线分为四段：

1. **数据产品化**：先定义企业、设备、文档体系、元数据和问题集。如果资料混乱，后面的 RAG 指标没有意义。
2. **系统持久化**：把当前“最近上传的一份 PDF + 内存 FAISS”升级为“多文档 + PostgreSQL/pgvector + 文档生命周期”。
3. **质量工程化**：使用事实题、流程题、跨文档题、版本题和无答案题验证检索、引用与拒答，而不是只看几次聊天效果。
4. **成果产品化**：用轻量页面、架构图、指标、演示视频和案例报告，把代码变成面试官与潜在客户能快速理解的作品。

## 五、每天两小时的固定节奏

普通开发日建议这样分配：

- 70 分钟：完成当天唯一的核心开发或数据任务。
- 25 分钟：测试、记录问题和更新文档。
- 25 分钟：录制关键操作、整理口播要点或剪一段视频素材。

视频发布日建议改为：

- 60 分钟：完成一个可展示的小里程碑并验证。
- 60 分钟：剪辑、字幕、封面、简介和发布。

每天结束前只记录三件事：今天完成了什么、遇到什么问题、明天的第一步是什么。开发时顺手录屏，周末再配音和剪辑，不要等功能全部完成后重演整个过程。

### 第三周：提升检索质量、引用和拒答能力（14 小时）

#### 本周目标

让系统不仅“能回答”，而且能证明为什么这样回答、什么时候不应该回答。

| 天数     | 2 小时任务                          | 当天结果           |
| ------ | ------------------------------- | -------------- |
| Day 15 | 完成结构化切块，保留标题、设备、版本和页码           | 更完整的 Chunk 元数据 |
| Day 16 | 建立向量检索基线，记录 Top-k、命中率和延迟        | 可复现基线结果        |
| Day 17 | 实现引用结构：文档、版本、页码、Chunk 与原文片段     | 可追溯回答          |
| Day 18 | 设计相似度阈值和无答案规则，强化 Prompt 的安全边界   | 可靠拒答逻辑         |
| Day 19 | 完成 50 道问题和标准答案/证据标注             | 评测集 v1.0       |
| Day 20 | 比较两组 Chunk、Top-k 或检索策略，输出指标     | 对照实验结果         |
| Day 21 | 修复主要失败案例；有余力再做关键词混合检索或 Reranker | 质量报告与视频素材      |

#### 评测集建议构成

| 问题类型    |  数量 | 验证目标           |
| ------- | --: | -------------- |
| 单文档事实题  |  15 | 能否召回明确参数和规定    |
| 操作流程题   |  10 | 步骤是否完整、顺序是否正确  |
| 故障诊断题   |  10 | 症状、原因、检查顺序是否对应 |
| 跨文档综合题  |   5 | 能否结合台账、SOP 和工单 |
| 版本与冲突题  |   5 | 是否只使用当前有效版本    |
| 无答案与越界题 |   5 | 是否可靠拒答而不是编造    |

至少记录以下指标：

- Recall@K：正确证据是否出现在前 K 个 Chunk。
- MRR：正确证据的排序是否靠前。
- 引用正确率：引用是否真的支持回答。
- 拒答正确率：无依据问题是否拒答。
- 端到端延迟：从提问到获得完整回答需要多久。

#### 本周必须交付

- 50 道带类型、标准答案和证据位置的固定评测集。
- 一份基线结果和一份优化后结果，所有数字由脚本真实运行产生。
- 回答必须返回文档、版本、页码、原文片段和相关度信息。
- 对无资料、旧版本和高风险越界问题有明确处理策略。
- 至少整理 5 个失败案例，说明失败原因和修复结果。

#### 本周验收

- 随机抽查 10 个可回答问题，引用可以定位回原文。
- 旧版本问题不会引用已停用文档。
- 5 个无答案问题不会生成看似合理的维修步骤。
- 评测脚本可重复运行，结果文件包含参数和运行时间。

#### B 站内容

- 第 5 条：《RAG 回答为什么必须带文档版本、页码和原文》
- 第 6 条：《我用 50 道题评测设备运维知识库：Recall@K、引用与拒答》

## 七、B 站教学系列的统一结构

每条视频控制在 6～12 分钟，使用同一套开头和章节结构：

1. 这期要解决的业务问题是什么。
2. 改造前的系统有什么限制。
3. 展示关键设计，不逐行念代码。
4. 现场运行一次接口、测试或评测。
5. 说明踩坑、取舍和下一步。

录制素材包括：

- 30～60 秒的功能前后对比。
- 一张本期数据流或结构图。
- 1～2 段关键代码讲解。
- 一次真实测试或失败案例。
- 本期 Git 提交或阶段成果截图。

视频标题优先强调成果和问题，例如“RAG 服务重启后索引为什么丢了”，少用“Day 12 学习记录”这类只有作者自己容易理解的标题。

## 八、最终演示脚本

控制在 3 分钟左右：

1. **背景（20 秒）**：虚构制造企业的设备资料分散，维修人员检索慢且容易参考旧版本。
2. **文档管理（35 秒）**：展示四类设备资料、文档版本、状态和处理进度。
3. **事实问答（30 秒）**：询问一个明确参数，展示文档、版本、页码和原文引用。
4. **综合问答（35 秒）**：结合故障指南与历史工单给出排查顺序。
5. **版本控制（25 秒）**：停用旧版规程，再次提问验证旧内容不被引用。
6. **拒答与安全（25 秒）**：询问资料中不存在或超出系统边界的问题，展示拒答。
7. **评测与架构（30 秒）**：展示真实 Recall@K、引用正确率、拒答正确率、延迟和架构图。
8. **总结（20 秒）**：说明已知限制、项目地址和下一步计划。

## 九、月底完成标准

只有同时满足下面四组条件，项目才算完成。

### 数据

- 资料覆盖四类设备和完整的运维知识类型。
- 来源登记清楚，虚构数据标识清楚，无真实敏感信息。
- 文档、台账、工单和版本通知之间没有明显自相矛盾。

### 系统

- 支持多文档、持久化、状态管理和版本过滤。
- 回答可以追溯到文档、版本、页码和原文。
- 服务重启后仍可检索，停用旧版后不会继续命中。
- 无答案时能拒答，关键异常有清楚提示。

### 评测

- 至少 50 道固定问题并可重复运行。
- 有真实的基线、对照实验、失败案例和结果文件。
- 不在简历、README 或视频中编造准确率、并发量和延迟数字。

### 展示

- README 能让别人复现。
- 有轻量页面、架构图、案例报告和 3 分钟演示视频。
- B 站阶段视频形成连续系列，而不是互不相关的技术片段。

## 十、时间不足时的降级顺序

如果进度落后，按下面顺序降级，不牺牲核心闭环：

1. 取消飞书机器人、复杂权限和高级统计。
2. 暂停 Reranker，只保留经过评测的向量检索。
3. 将异步任务简化为带状态的 FastAPI 后台任务。
4. 前端只保留文档列表、问答和引用查看三个页面。
5. 资料数量可从 25 份降到 15 份，但不能删除版本题、无答案题和来源登记。

无论如何不要省略：持久化、多文档、版本引用、固定评测、数据合规说明和最终演示。这六项才是本项目区别于普通“上传 PDF 聊天 Demo”的核心成果。
