# 17 天“可评测企业 RAG 后端”求职冲刺计划

## 一、当前真实起点与项目定位

本计划只以仓库当前代码为依据，不参考既有 Day 1、Day 2 学习文件，也不修改现有简历中的另一个项目。

当前已经实际具备：

- FastAPI 接口和 Pydantic 数据校验。
- PDF 文本提取、字符切块、中文 Embedding。
- FAISS 内存向量检索和 Top-3 RAG 问答。
- 回答返回原文、页码和相似度。
- SQLite 普通聊天历史。
- 12 道基础评测及 Top-1/Top-3 对照结果。
- Dockerfile。
- PostgreSQL + pgvector 的 Docker Compose 环境。

当前主要缺口：

- 应用尚未真正连接 PostgreSQL。
- 没有 SQLAlchemy、Alembic 和 pgvector 数据访问代码。
- 只能保存最近上传的一份 PDF，重启后索引丢失。
- 没有多知识库、多文档和检索范围过滤。
- 没有正式自动化测试。
- 当前评测数据规模小、业务感较弱。
- 缺少独立的项目演示、求职版项目描述和面试材料。

项目最终定位为：

> 基于 FastAPI、PostgreSQL/pgvector 和中文 Embedding 的可持久化、可评测企业制度 RAG 后端。

这个项目与现有简历中的 Agent 项目分开：Agent 项目体现工具调用和应用交互；当前项目重点体现 RAG 原理、后端工程、数据库、评测和问题分析。

## 二、17 天最终成果

投递前必须形成以下闭环：

1. 支持创建知识库并上传多份 PDF。
2. Chunk、元数据和向量持久化到 PostgreSQL/pgvector。
3. 服务重启后不需要重新上传即可继续问答。
4. 检索时明确限定知识库，不会跨知识库返回数据。
5. 回答来源可以定位到文档、页码、Chunk 和原文。
6. 对资料不足的问题能够拒答。
7. 使用固定问题集报告 Recall@K、MRR、拒答正确率和延迟。
8. 关键链路具有 pytest 测试。
9. README 可以指导他人运行和复现实验。
10. 提供三分钟演示视频、新项目简历条目和面试问答稿。

不以“功能数量”作为成功标准，以“能运行、能验证、能解释”为成功标准。

## 三、最小实现范围

### 3.1 数据模型

只实现三个核心实体：

#### knowledge_bases

- `id`
- `name`
- `created_at`

#### documents

- `id`
- `knowledge_base_id`
- `filename`
- `status`
- `page_count`
- `chunk_count`
- `created_at`

#### chunks

- `id`
- `document_id`
- `page`
- `chunk_index`
- `text`
- `embedding vector(512)`

文档状态固定为：

- `processing`
- `ready`
- `failed`

只有 `ready` 文档能参与检索。上传失败时保留失败状态，但不能留下可检索的部分 Chunk。

### 3.2 API 调整

将现有单文档 RAG 接口迁移为：

- `POST /knowledge-bases`
- `GET /knowledge-bases`
- `POST /knowledge-bases/{kb_id}/documents`
- `GET /knowledge-bases/{kb_id}/documents`
- `POST /knowledge-bases/{kb_id}/chat`
- `GET /health`

问答请求：

```json
{
  "question": "出差住宿标准是多少？",
  "top_k": 3
}
```

`top_k` 默认值为 3，允许范围为 1～10。

来源统一返回：

```json
{
  "document_id": "...",
  "document_name": "差旅报销制度.pdf",
  "page": 2,
  "chunk_id": "...",
  "text": "原文片段",
  "score": 0.82
}
```

现有 `/chat` 和 `/history` 保持不变，但不作为当前项目的主要演示内容。原 `/upload`、`/rag/chat` 不再维护独立的全局 FAISS 链路；新接口验证完成后，统一使用数据库检索服务。

### 3.3 检索和拒答

- 文档向量继续使用 `BAAI/bge-small-zh-v1.5`，维度保持 512。
- PostgreSQL 使用 cosine distance 查询。
- SQL 查询必须先限制知识库和 `ready` 状态，再计算 Top-K。
- `score` 统一转换为“数值越高越相关”。
- 根据固定评测集选择拒答阈值。
- 最高分低于阈值时，直接返回“知识库中没有足够依据”，不调用 LLM。
- 阈值和 Top-K 一旦通过实验确定，就写入配置并固定，不针对演示问题临时调整。

## 五、测试与验收场景

至少覆盖以下场景：

- 一个知识库连续上传多份 PDF，可以跨文档检索。
- 两个知识库包含相似内容时，查询 A 不返回 B 的内容。
- API 和 PostgreSQL 重启后，已有文档仍然可查询。
- `processing` 和 `failed` 文档不参与检索。
- 上传失败不会留下部分可检索 Chunk。
- 空文件、错误扩展名、无文字 PDF 和不存在的知识库返回明确错误。
- `top_k=0`、`top_k>10` 和空问题通过数据模型拒绝。
- 每条来源都能人工定位到正确文档和页码。
- 无答案问题不会调用 LLM，也不会返回无关来源。
- 数据库不可连接时错误中不泄露连接密码。
- 固定评测脚本可重复运行并生成相同结构的报告。

最终演示顺序固定为：

1. 展示系统架构。
2. 创建一个制度知识库。
3. 上传三份制度 PDF。
4. 提问一个跨文档问题。
5. 核对回答引用。
6. 提问一个无答案问题并展示拒答。
7. 重启服务后再次提问。
8. 展示评测报告和失败案例。

## 六、求职表达

当前项目是自己从需求分析、架构设计到编码和评测完整实现的独立项目，应作为一个新的项目经历加入简历，不修改或替换已有 Agent 项目。简历不能把它定义成“对旧 Demo 的改造”，而要呈现为一个完整的企业知识库 RAG 后端；单文档 FAISS 版本只是开发过程中用于验证最小链路的早期基线。

### 6.1 简历项目定位

建议项目标题：

> 企业制度与 SOP 智能知识库 RAG 后端｜独立开发

建议用一句话说明业务价值：

> 面向企业制度、报销规范和操作流程查询场景，独立设计并实现支持多知识库、多文档持久化检索、可追溯引用和无依据拒答的 RAG 后端系统。

项目完成后，简历保留以下三条高信息量描述：

- **完整 RAG 链路**：基于 FastAPI 独立实现 PDF 解析、文本切分、BGE 中文 Embedding、PostgreSQL/pgvector 向量检索和大模型问答，支持多知识库、多文档管理，并返回文档名称、页码、Chunk 和原文等可追溯来源。
- **数据与可靠性设计**：设计知识库、文档和 Chunk 数据模型，在检索阶段执行知识库范围及文档状态过滤；通过处理状态、数据库事务和失败回滚避免半成品数据参与问答，并验证服务重启后的数据恢复能力。
- **评测与工程交付**：建立固定企业制度评测集，对比 Top-1/3/5 并报告真实 Recall@K、MRR、拒答正确率和检索延迟；使用 pytest 覆盖关键链路，并通过 Docker Compose、README 和演示脚本提供可复现运行方式。

这些内容是项目完成后的目标写法。投递前必须根据实际完成情况删减，所有指标只能在 Day 11 实测后填写，不能提前编造，也不能把尚未实现的功能写入简历。

### 6.2 面试讲述主线

面试时不从“我改了一个旧项目”开始，而按照完整项目的形成过程讲述：

1. **业务问题**：企业制度分散在多份 PDF 中，人工查询慢，普通大模型又可能脱离制度编造答案，因此需要带来源、能拒答的知识库问答系统。
2. **总体设计**：说明上传链路和问答链路，画出 FastAPI、PDF 解析、Chunk、Embedding、PostgreSQL/pgvector、LLM 和来源引用之间的数据流。
3. **关键实现**：解释文档、Chunk、向量和来源如何关联，多知识库如何隔离，文档状态和事务如何避免失败数据进入检索。
4. **技术选择**：说明为什么选用 BGE 中文 Embedding、pgvector cosine distance、固定 Top-K，以及 PostgreSQL 同时保存业务元数据和向量的取舍。
5. **质量验证**：展示固定问题集、Recall@K、MRR、拒答正确率、延迟和失败案例，说明 Top-K 与拒答阈值是如何通过实验确定的。
6. **限制与演进**：诚实说明当前只支持文本型 PDF、同步处理和知识库级隔离；如果继续开发，再加入异步任务、文档版本、用户认证和 RBAC。

### 6.3 如何使用早期 FAISS 版本

早期单文档 FAISS 实现可以在面试中作为技术演进证据，但不能成为简历对整个项目的定义。推荐表达为：

> 我先用 FastAPI、BGE 和 FAISS 跑通 PDF 上传、切块、检索、生成与引用的最小闭环；在验证 RAG 链路后，根据多文档管理、重启恢复和检索范围过滤的需求，进一步设计 PostgreSQL/pgvector 的持久化架构。

这种讲法既能说明项目确实由自己逐步完成，也能体现需求驱动的架构演进，而不是把完整项目缩写成一次数据库替换。
