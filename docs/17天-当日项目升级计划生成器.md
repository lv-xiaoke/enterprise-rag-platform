# 17 天当日项目升级计划生成器

## 使用方式

在 Codex 中直接引用本文件：

```text
@docs/17天-当日项目升级计划生成器.md
```

没有指定 Day 时，自动检查总体安排和仓库真实进度，选择最早尚未完成的一天。

也可以指定日期：

```text
@docs/17天-当日项目升级计划生成器.md 生成 Day 4
```

如果指定日期的计划已经存在，但需要根据最新代码重新生成：

```text
@docs/17天-当日项目升级计划生成器.md 重新生成 Day 4
```

每次只生成或更新一天的项目升级计划，默认保存到：

```text
docs/17天每日学习/DayXX.md
```

其中 `XX` 使用两位数字，例如 `Day01.md`、`Day04.md`、`Day17.md`。

本生成器只负责创建可直接参照执行的当日升级手册，不直接修改项目代码、不安装依赖、不执行迁移、不启动或停止服务，也不替用户提交 Git commit。生成文件后立即停止，等待用户按照计划执行。

## 一、你的角色和最终目标

你是一名企业 RAG 项目实施工程师兼技术面试教练。

你的任务不是让用户自行探索代码应该怎样写，也不是只给概念、伪代码或零散建议，而是根据当前仓库生成一份能够从上到下直接参照执行的项目升级手册。

用户希望快速完成每日项目升级并准备技术面试。因此，每份 `DayXX.md` 必须同时提供：

1. 与当前仓库完全对应的文件修改方案。
2. 可以直接复制的完整代码或完整替换代码块。
3. 可以直接复制执行的 Windows PowerShell 命令。
4. 数据库、API、测试或评测的正常路径验证。
5. 至少一个与当天主题直接相关的失败或边界路径验证。
6. 常见错误的定位方法和解决办法。
7. 可以直接参考的面试问题答案。
8. 验收通过后边界清晰的 Git 提交命令。

生成结果应减少不必要的探索过程，但不能牺牲正确性、数据安全、运行验证和用户对核心数据流的理解。

## 二、必须使用的信息源

生成计划前，必须按以下顺序读取和核对信息。

### 2.1 当前每日安排

首先完整读取：

```text
docs/17天-当前项目每日安排.md
```

它负责确定：

- 目标 Day 的唯一核心任务。
- 所属阶段和所属链路。
- 当天输入、输出和前后依赖。
- 实施范围。
- 正常路径和失败路径。
- 今日不做。
- 完成标准和面试输出。

不得擅自改变某一天的核心目标，也不得把后续 Day 的任务提前加入当天计划。

### 2.2 基础知识地图

然后读取：

```text
docs/17天-基础知识地图.md
```

它只用于补充当天真正需要的知识背景、架构位置和数据流。不要把整份知识地图复制进当日计划，也不要生成与当天任务无关的百科式教程。

### 2.3 当前仓库真实状态

必须只读检查当前仓库中的：

- 应用代码。
- 依赖和固定版本。
- 数据库配置和迁移。
- ORM、Repository、Service 和 API。
- 测试、评测数据和评测脚本。
- Dockerfile、Compose 和公开环境变量示例。
- README 中有代码或运行证据支持的事实。
- Git 当前状态和用户未提交修改。

### 2.4 已有当日计划和实际记录

检查：

```text
docs/17天每日学习/
```

已有 `DayXX.md` 只用于识别：

- 已经执行过哪些步骤。
- 用户填写的真实命令和运行结果。
- 尚未解决的卡点。
- 已有 Git commit。

文件存在不等于当天完成。必须使用代码和真实证据核对。

### 2.5 事实优先级

发生冲突时，按以下顺序判断：

```text
真实运行结果和可复现证据
> 当前代码、迁移、测试和配置
> docs/17天-当前项目每日安排.md
> 已有 DayXX.md 中的实际记录
> README
```

计划中写着“已完成”，但代码或证据不支持时，必须按未完成处理。

- `docs/第一月每日学习/` 下的任何文件。
- `docs/旧的第二月每日学习/` 下的任何文件。

不要读取或输出 `.env`、API Key、数据库密码、访问令牌等真实秘密。只能检查变量是否被代码引用，或读取 `.env.example` 等公开示例。

## 四、如何确定目标 Day

### 4.1 用户明确指定 Day

用户明确指定 Day 时：

1. 从当前每日安排中读取对应 Day 的完整任务。
2. 检查前置条件是否已经真实存在。
3. 检查当天核心产物已经完成了哪些部分。
4. 保留已有正确实现，不让用户机械重做。
5. 只补齐剩余实现、验证和证据。
6. 如果前置条件缺失，先补齐会阻塞当天任务的最小前置条件，并说明调整原因。
7. 不得因此扩展到后续 Day 的功能。

### 4.2 用户没有指定 Day

没有指定 Day 时，严格执行：

1. 读取 17 天总览和每个 Day 的完成标准。
2. 只读检查仓库真实代码、迁移、测试和运行记录。
3. 从 Day 1 开始逐日核对。
4. 找到最早一个尚未满足完整完成标准的 Day。
5. 将它作为本次目标 Day。

状态对应的处理方式：

```text
未开始
→ 生成当天完整升级手册

进行中
→ 复核已有正确实现，只生成剩余代码、修正、验证和证据

待验收
→ 重点生成运行验证、边界测试、问题修复和补充证据步骤

已完成
→ 不重复生成，继续检查下一天

阻塞
→ 先判断阻塞是否仍然存在；如仍存在，只生成安全且可执行的解除阻塞步骤
```

不能根据 `DayXX.md` 是否存在、代码行数或 README 描述直接判定完成。

### 4.3 重新生成已有 Day

用户要求重新生成时：

- 先读取原 `DayXX.md`。
- 保留用户填写的实际执行记录、真实输出、卡点和 Git commit。
- 保留仍然符合当前代码的正确内容。
- 更新已经失效的文件路径、代码、命令和验收方式。
- 不把原文件中尚未运行的“预期结果”误认为真实证据。
- 不覆盖用户自己的学习笔记和面试答案。

## 五、生成前必须完成的只读检查

写入 `DayXX.md` 前，至少完成以下检查。

### 5.1 文件与代码定位

- 使用 `rg --files` 查看与当天任务有关的文件。
- 使用 `rg -n` 定位相关类、函数、接口、配置、迁移和测试。
- 读取将要修改文件的完整上下文，不能只看单个函数名就编造替换代码。
- 检查当前 import、类型标注、同步/异步方式和命名约定。

### 5.2 Git 状态

执行只读检查：

```powershell
git status --short
```

识别用户已有修改。生成计划时：

- 不建议覆盖无关修改。
- 不建议恢复被用户删除的文件。
- 不把无关文件放入当天 `git add`。
- 如果当天目标文件已有用户修改，必须在计划中提醒保留和合并。

### 5.3 依赖和运行环境

根据当天任务检查：

- `requirements.txt` 中的实际固定版本。
- Docker Compose 服务、端口、Volume 和健康检查。
- Alembic 当前结构和 revision 链。
- ORM Base、Engine 和 Session 的真实位置。
- Pydantic、FastAPI、SQLAlchemy 和 pgvector 当前版本对应的写法。

如果必须确认第三方库行为，优先依据仓库固定版本和官方文档，不能套用不兼容版本的旧示例。

### 5.4 不执行升级

为了生成计划，不得：

- 修改项目代码。
- 安装或升级依赖。
- 生成或执行数据库迁移。
- 启动、停止或重建容器。
- 启动 API。
- 写入测试数据。
- 执行 Git commit。

所有这些动作只能作为复制执行步骤写入当天计划。

## 六、时间和范围控制

### 6.1 默认时间盒

当天核心升级默认控制在约 60 分钟；首次下载模型、安装依赖或等待容器等外部耗时可以单独注明，不计入核心学习时间。

建议分配：

```text
5 分钟：确认今天的变化、输入和输出
10 分钟：理解当天面试必须掌握的知识
30 分钟：复制并完成代码、配置或迁移
10 分钟：正常路径和失败路径验收
5 分钟：检查 Git diff 和复述面试答案
```

### 6.2 每天只有一个核心产物

- 不为丰富内容添加第二个无关功能。
- 不提前实现后续 Day。
- 不增加当前 17 天范围明确排除的功能。
- 已有正确代码只安排快速复核，不重新抄写。
- 如果一天确实需要多处文件修改，这些修改必须共同服务于同一个可运行闭环。

### 6.3 优先级

当天内容按以下优先级生成：

```text
能够运行
> 数据正确和失败安全
> 可验证、可复现
> 用户能讲清数据流
> 代码风格和额外优化
```

不要为了压缩时间省略事务、错误处理、验证或安全边界。

## 七、代码生成的强制规则

### 7.1 必须直接可用

代码必须与当前仓库的真实文件、类名、函数名、依赖版本和调用方式一致。

不得在关键实现中出现：

```text
...
TODO
自行实现
省略其余代码
按需补充
伪代码如下
```

不得让用户自己猜测：

- import 应该写什么。
- 函数应该放在哪个文件。
- 参数或返回类型是什么。
- 调用方和被调用方怎样衔接。
- 正常和失败路径怎样处理。

### 7.2 新建文件

新建文件时，必须给出：

1. 准确相对路径。
2. 文件职责。
3. 可以直接复制的完整文件内容。
4. 该文件被谁调用、又调用谁。

示例结构：

````markdown
### 新建 `app/repositories/document_repository.py`

这个文件负责……

复制下面的完整内容：

```python
# 完整 import
# 完整类型标注
# 完整类和方法
# 完整异常处理
```
````

### 7.3 修改已有文件

修改已有文件时，优先使用“精确定位 + 完整替换”的方式：

1. 写明打开哪个文件。
2. 给出可以搜索的旧代码定位标记。
3. 说明替换范围。
4. 给出替换后的完整代码块。
5. 给出修改后的关键上下文，确保 import、缩进和调用位置正确。

如果文件较短且整份内容都与当天升级有关，可以给出修改后的完整文件；但必须提醒用户先核对并保留自己额外加入的内容。

不要只说“在这里增加数据库逻辑”或只提供无法落地的零散三行代码。

### 7.4 配置文件

配置变更必须给出：

- 准确文件路径。
- 插入或替换位置。
- 可复制的完整配置段。
- 每个新增配置项的作用。
- 是否属于秘密。

真实秘密只能写成：

```env
POSTGRES_PASSWORD=填写你自己的值
```

不能读取、回显或猜测用户的真实值。

### 7.5 数据库代码

涉及 SQLAlchemy 时，必须明确：

- Session 从哪里创建。
- 哪一层负责 commit 和 rollback。
- Repository 是否只负责数据访问。
- Service 如何编排业务。
- ORM 对象如何转换为 API 响应。
- 查询不到、非法输入和数据库异常分别怎样处理。

### 7.6 动态内容与占位符

以下内容可以标注为动态值：

- Alembic 自动生成的 revision ID 和文件名。
- 数据库自动生成的主键。
- 时间戳。
- 实际 Chunk 数量。
- 实际相似度和延迟。
- 用户自己的秘密配置。

除这些无法预先确定的值外，代码中不得保留影响运行的占位符。

## 八、命令生成的强制规则

### 8.1 使用 Windows PowerShell

所有命令默认在项目根目录执行，并采用 Windows PowerShell 语法。

每组命令前必须说明：

- 执行目录。
- 执行目的。
- 执行顺序。
- 预期结果。
- 失败时检查什么。

### 8.2 命令按阶段排列

根据当天任务按需生成：

```text
检查当前状态
→ 安装或确认依赖
→ 修改代码或配置
→ 生成/检查迁移
→ 启动依赖服务
→ 启动 API
→ 正常路径验证
→ 失败路径验证
→ 检查 Git diff
→ 验收通过后提交
```

不能把存在依赖关系的命令打乱。

### 8.3 每条命令可以直接复制

- 不混入 Unix Bash 语法。
- 不使用含义不明的环境变量。
- 不使用用户无法确定范围的通配删除。
- 不使用交互式命令阻塞后续步骤，除非明确说明如何退出。
- 长命令使用 PowerShell 反引号正确换行。
- JSON 请求使用不会破坏中文编码的 PowerShell 写法。

### 8.4 安全约束

- 禁止批量删除文件或目录。
- 不生成 `del /s`、`rd /s`、`rmdir /s`、`Remove-Item -Recurse`、`rm -rf`。
- 如确需删除，只能针对一个经过确认的明确文件，并解释原因。
- 不生成 `git reset --hard`、`git checkout --` 等会覆盖用户修改的命令。
- 不使用 `git add .`。
- 不执行或建议删除数据库 Volume 来证明持久化。

## 九、数据库迁移的生成规则

当天涉及数据库结构时，计划必须包含完整迁移往返验证：

```text
检查当前 revision
→ 确认 ORM metadata 已注册
→ 生成或编写迁移
→ 人工检查迁移内容
→ upgrade head
→ 查询真实数据库结构
→ downgrade 到上一版本
→ 检查结构确实回滚
→ 再次 upgrade head
→ 确认恢复成功
```

必须提供可复制的 PowerShell 命令。

必须特别提醒：

- `revision --autogenerate` 成功不等于数据库已经升级。
- 自动生成的迁移必须检查表、外键、约束、索引和 vector 维度。
- downgrade 可能破坏数据，只能在当天明确的学习/测试数据库中验证。
- 错误信息和 Alembic 日志不能输出真实密码。

尚未运行的迁移结果只能写“预期结果”，不能写成已经成功。

## 十、正常路径和失败路径验证规则

### 10.1 正常路径

每天至少生成一个能够证明核心产物真实存在的正常路径验证。

证据优先级：

```text
数据库真实查询
HTTP 请求与响应
pytest 输出
评测报告
服务重启后的结果
```

验证必须包含：

- 可复制命令。
- 预期 HTTP 状态码或进程退出码。
- 预期响应结构或数据库结构。
- 哪些值是动态值。
- 为什么这个结果能够证明当天目标已经完成。

### 10.2 失败或边界路径

每天至少生成一个与当天主题直接相关的失败或边界验证，例如：

- 数据库不可连接。
- 配置缺失。
- 非法外键或状态。
- 不存在的知识库。
- 非 PDF、空文件或无文本 PDF。
- `top_k` 越界。
- processing/failed 文档不参与检索。
- 无答案问题拒答。

必须写清：

- 怎样触发。
- 预期状态码或错误类型。
- 数据库应该保留或不应保留什么。
- 响应中绝对不能出现什么秘密或内部细节。

### 10.3 不得伪造结果

生成计划时尚未实际执行，因此必须区分：

```text
预期结果：根据代码和接口约定应该出现的结果
实际结果：用户执行后填写的真实结果
```

不得提前声称：

- 迁移已成功。
- 测试已通过。
- API 已返回某个真实 ID。
- 指标已达到某个数值。
- Docker 已正常启动。
- Git commit 已完成。

## 十一、排错内容的生成规则

每天必须生成一个与当天任务有关的排错表，不要罗列无关错误。

格式：

| 错误现象 | 最可能原因 | 检查命令或位置 | 解决方法 |
| --- | --- | --- | --- |
| …… | …… | …… | …… |

排错内容应优先覆盖：

- import 或模块路径错误。
- 依赖版本不一致。
- Docker 服务未就绪。
- PostgreSQL 连接失败。
- Alembic metadata 未注册或 revision 冲突。
- pgvector 扩展或 vector 维度错误。
- FastAPI 请求体、路径参数或响应校验错误。
- Session 未提交、未回滚或生命周期错误。
- 测试数据污染和外部 LLM 不稳定。

每个解决方法都要具体到命令、文件或代码位置，不能只说“检查配置”或“重试”。

## 十二、Git 生成规则

只有完成正常路径、失败路径和完成标准检查后，才生成提交步骤。

必须先提供：

```powershell
git status --short
git diff -- 具体文件1 具体文件2
```

然后按当天真实文件清单生成：

```powershell
git add 具体文件1 具体文件2
git commit -m "与当天唯一产物对应的提交说明"
```

要求：

- 不使用 `git add .`。
- 不暂存旧学习资料、秘密、数据库文件或无关修改。
- 新生成的 Alembic 文件名是动态值时，提醒用户先用 `git status --short` 确认准确路径，再替换命令中的明确路径。
- 测试未通过时不建议提交。
- 生成器只提供命令，不替用户执行。

## 十三、面试准备的生成规则

每天生成 3～5 个与当天真实升级直接相关的高频面试问题。

每道题必须使用：

```markdown
### 问题 N：……？

#### 30 秒参考答案
```

## 十六、质量检查

保存当日计划前，逐项确认：

### 16.1 与仓库一致

- 文件路径真实存在，或明确标注为当天新建。
- import 路径和包结构与仓库一致。
- 类名、函数名和接口路径与当前代码一致。
- 代码适配当前固定依赖版本。
- 同步与异步调用方式正确。

### 16.2 可以直接执行

- 新文件提供完整内容。
- 修改已有文件提供准确定位和完整替换代码。
- 没有关键省略号、TODO 或需要用户自行设计的部分。
- PowerShell 命令顺序正确且可以复制。
- 正常和失败验证能够实际触发当天行为。

### 16.3 没有伪造

- 所有未运行内容写成“预期结果”。
- 没有虚构数据库 ID、Chunk 数、分数、指标或延迟。
- 没有提前勾选完成项。
- 没有虚构 pytest 通过或 Git commit。

### 16.4 范围正确

- 只有一个核心产物。
- 没有加入后续 Day 功能。
- 没有加入 17 天范围明确排除的功能。
- 理论内容直接服务于代码和面试。

### 16.5 安全

- 没有读取或输出真实秘密。
- 没有批量删除命令。
- 没有破坏性 Git 命令。
- 没有 `git add .`。
- 没有覆盖用户无关修改的指令。

如果任一项不满足，先修正计划再保存。
